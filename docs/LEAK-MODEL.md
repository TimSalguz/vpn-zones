# Модель утечек и герметичная архитектура

Здесь зафиксировано, откуда из зоны вообще может утечь трафик или метаданные, и
целевая архитектура, при которой утечки невозможны **по построению** — для
любого семейства протоколов (v4, v6, любое гипотетическое будущее). Bash-версия
закрывает известные дыры заплатками (см. CHANGELOG); Rust-ядро (ROADMAP M1)
обязано реализовать целевую архитектуру сразу.

## Каналы утечки

1. **Маршруты мимо туннеля.** Классика: в туннель завёрнут только v4 default,
   а pasta даёт зоне полную связность с хостом — весь IPv6-трафик шёл в обход
   VPN (закрыто заплаткой M0: v6 либо в туннель, либо выключен целиком). Тот же
   класс: прямой доступ к LAN-подсети хоста и /32-маршрут до endpoint (туннелю
   он нужен, но виден и приложениям).
2. **DNS.** resolv.conf хоста с локальным резолвером; кэширующий nsncd, к
   которому glibc ходит по **unix-сокету** — это не IP, маршрутами не
   закрывается (закрыто: tmpfs поверх /run/nscd); стаб systemd-resolved.
3. **Не-IP каналы.** unix-сокеты хоста в $XDG_RUNTIME_DIR (композитор, D-Bus,
   pipewire), Secret Service через шину, X11. Сетью не закрываются в принципе —
   их закрывают слои wl-sandbox / fs-sandbox / xdg-dbus-proxy.
4. **Деградация.** Туннель умер, приложения живы. Должно быть fail-closed
   (маршруты продолжают смотреть в мёртвый туннель — пакеты дропаются, а не
   обходят) и заметно (уведомления — M5).

## Целевая архитектура: шлюзовой namespace

Принцип: **утечка невозможна не потому, что запрещена правилом, а потому, что
пути физически не существует.** Namespace приложений содержит ровно два
интерфейса: lo и туннельный. Других интерфейсов и маршрутов — любого семейства
— там нет вовсе.

```
хост ── pasta ── [uplink-ns]   ← связность с миром живёт ЗДЕСЬ
                    │   UDP-сокет WireGuard / userspace-клиент
                    │   (sing-box, OpenVPN, чужой GUI-клиент)
                    │   tun/awg0 создаётся здесь и ПЕРЕЕЗЖАЕТ ↓
                 [app-ns]      ← только lo + туннельный интерфейс
                    └── приложения
```

- **Ядерный WireGuard/AmneziaWG.** Документированное свойство WireGuard:
  UDP-сокет туннеля живёт в namespace, где интерфейс был **создан**, и не
  переезжает вместе с ним. Создаём awg0 в uplink-ns, переносим в app-ns
  (`ip link set awg0 netns …`), конфигурируем внутри. Шифрованные пакеты
  рождаются в uplink-ns; app-ns не имеет даже маршрута до endpoint.
- **Userspace-клиенты (sing-box/xray, OpenVPN, произвольный GUI-клиент).**
  Тот же контур — «VPN-клиент в контейнере»: клиент работает в uplink-ns, на
  входе у него связность через pasta, на выходе tun, который переезжает в
  app-ns (или veth-пара, если клиент не отдаёт tun). Приложения не видят ни
  процесса клиента, ни его настоящего трафика — только готовый интерфейс.
- Приложения входят в app-ns без capabilities (CapEff=0): включить v6 обратно,
  добавить маршрут или интерфейс они не могут. Вложенный user namespace даёт
  процессу власть только над его **новыми пустыми** ns, не над app-ns
  (для CAP_NET_ADMIN над app-ns нужны права в userns-владельце, которых нет).

Следствия:
- killswitch перестаёт быть свойством маршрутизации и становится топологией;
- LAN из app-ns недоступна вовсе; доступ — только явной опцией через uplink-ns;
- handshake-трафик и endpoint не видны приложениям;
- новое семейство протоколов («IPv8») ничего не меняет: пути нет.

## Второй эшелон: nftables (M3)

Ошибки конфигурации случаются, поэтому поверх топологии — фильтр:
- в app-ns: egress только через туннельный интерфейс (default deny);
- в uplink-ns: наружу только трафик протокола туннеля до endpoint (+ DNS
  bootstrap для резолва имени endpoint, если он именной).

## DNS

- resolv.conf app-ns — только резолверы, достижимые через туннель: из конфига
  или дефолт 1.1.1.1/9.9.9.9 (заплатка M0); bind-mount виден только зоне.
- nsncd/nscd: unix-сокет прячется tmpfs-ом (сделано, см. GOTCHAS §3).
- Опция M3: локальный DoT/DoH-форвардер, чтобы содержимое DNS-запросов не
  читалось на выходе туннеля.

## Статус слоёв

| слой | bash-версия (сейчас) | цель |
|---|---|---|
| v4-маршруты | default в туннель, /32 до endpoint виден | uplink-ns |
| IPv6 | в туннель, если затуннелен; иначе выключен (M0) | uplink-ns, симметрично v4 |
| DNS | свой resolv.conf, сокрытие nsncd, дефолт-резолверы | + DoT/DoH опция |
| LAN | доступна напрямую | недоступна, opt-in |
| seccomp | нет (в bash невозможен) | M2, фильтр по образцу flatpak |
| фаерволл | нет | M3, nftables в обоих ns |
| мониторинг смерти туннеля | нет | M5 |
