# Всё по умолчанию в контейнерах (M8) — дизайн

English: [CONTAINERS.md](CONTAINERS.md) · Связанные документы:
[LAUNCHERS.ru.md](LAUNCHERS.ru.md) (ярлыки), [CERTIFICATES.ru.md](CERTIFICATES.ru.md)
(доверие по контейнерам), [LEAK-MODEL.md](LEAK-MODEL.md), [GOTCHAS.md](GOTCHAS.md)

**Статус: дизайн принят с решениями владельца от 2026-09-17 (§12).** Всё, что
названо здесь «новым», ещё не существует, если не помечено «сделано».

## 1. Коротко

Сегодня запуск — это три независимых выбора на каждый клик: сеть (зона,
unconfined, offline), контейнер данных (основной, профиль-оверлей, одноразовый) и
песочница файловой системы (нет, своя, именованная, разовая). Дизайн сводит
три оси в одну сущность — **контейнер**:

> Контейнер — это именованная личность: дом, набор разрешений, набор доверенных
> сертификатов **и одна сеть в каждый момент**. Экземпляр программы работает
> ровно в одном контейнере. Программы назначаются контейнерам, сети — тоже
> контейнерам, и оба назначения можно менять когда угодно — явно, а не побочным
> эффектом клика.

Следствия, по важности:

1. **Личность меняет сеть, только когда человек так решил**
   ([LEAK-MODEL](LEAK-MODEL.md), «Открытые каналы» §4). Вопрос о сети на каждый
   клик — ровно то, чем один профиль браузера незаметно уезжал в две сети;
   смена сети теперь отдельное действие и так и показывается.
2. **Ни один слой не теряется молча.** Любой запуск идёт одной дорогой — в зону,
   в `direct` или в `offline`. Баг с `direct`, исправленный в `fix/launch-path`
   (пикер терял контейнер, песочницу и ограничение композитора), — ровно тот
   класс, который так исключается по построению.
3. **У каждой программы по умолчанию свой дом**, а два контейнера можно
   объединить в один (§3.4).
4. **Запуски мимо лаунчера попадают в нужный контейнер**: D-Bus-активация,
   автозапуск, бинды композитора, ссылки из других программ, записи, которые
   программы пишут в пользовательский каталог (§5).
5. **Ярлыки на каждую зону объявлены устаревшими**; их заменяет вид по
   контейнерам ([LAUNCHERS.ru.md](LAUNCHERS.ru.md) §4).
6. **Всё декларативно** через опции home-manager-модуля, а машиночитаемое
   состояние говорит, откуда взято каждое значение (§8, §9).

## 2. Что есть сегодня

| понятие | где живёт | что изолирует |
|---|---|---|
| зона | `~/.local/state/vpn-zones/<зона>/` + `vpn-zone@<зона>` | сеть (в app-ns только `lo` и туннель); WireGuard, AmneziaWG или OpenConnect |
| `unconfined` | нигде | ничего (сеть хоста) |
| `offline` | зона с маркером, создаётся по требованию | всё сетевое, включая резолверы хоста |
| контейнер-слой (`home = layer`, был «профиль») | `~/.local/state/vpn-profiles/<имя>/` (данные), `~/.config/vpn-zones/containers/<имя>/` (настройки) | весь дом, под своим слоем (`<имя>/home/upper`); выданный путь пишется в настоящий дом; чужие хранилища не видны (до 2026-09-26 — только XDG-каталоги) |
| одноразовый контейнер | `~/.local/state/vpn-zones/.throwaway/vpn-profile-*` | то же, стирается за последним жильцом |
| контейнер со своим домом (`home = private`, была «именованная песочница») | `~/.local/state/vpn-profiles/<имя>/home` (данные — один каталог данных всех контейнеров, с 2026-09-26; до того `vpn-sandboxes/<имя>`), `~/.config/vpn-zones/containers/<имя>/` (настройки) | весь дом, шина, runtime-каталог, seccomp, X11 |
| контейнер основного дома (`home = main`) | только настройки | ничего из дома: своя сеть, программы и разрешения под именем |
| своя песочница программы | именованная песочница `app-<ключ>` | то же |
| разовая песочница | tmpfs | то же, стирается при выходе |
| ограничение композитора | `wl-sandbox`, включено по умолчанию | захват экрана, эмуляция ввода, фоновый буфер обмена |

Пикер помнит всё по программе: `.pinned`/`.last` (сеть) и
`.pinnedprofile`/`.lastprofile` (контейнер). Оси независимы — и именно поэтому
личность одной программы может переезжать между сетями. **С 2026-09-26 сеть —
у контейнера** ([PERMISSIONS.md](PERMISSIONS.md) §11.8): `.pinned` больше нет
(один раз перенесено в сети контейнеров), контейнер без сети спрашивает её при
первом запуске и привязывается, «всегда» в основном доме переводит программу в
`main-<сеть>` — контейнер основного дома, привязанный к ней. `.last` говорит
только, с чего начинается вопрос.

## 3. Модель

### 3.1 Контейнер

```
контейнер = {
  имя          уникальное; селектор — тот, что уже пишет реестр
  дом          private | overlay | throwaway-private | throwaway-overlay
  сеть         одна сеть (§3.3) или ask
  маршруты     дополнительные именованные маршруты рядом с сетью (LAN, …) — выключены
  разрешения   файлы {downloads, documents, pictures, home, paths[]}, x11,
               композитор {restricted | full}, (позже) имена шины, устройства
  доверие      дополнительные корневые сертификаты (CERTIFICATES.ru.md)
  программы    назначенные сюда (id ярлыков)
  источник     nix (только чтение) | local (CLI/GUI)
}
```

- **`дом`** один в один ложится на то, что есть: `private` — сегодняшняя
  именованная песочница (и своя `app-<ключ>`), `overlay` — сегодняшний профиль,
  одноразовые виды — сегодняшние `--fs-sandbox` и `--tmp-profile`. Каталоги
  данных остаются на местах: это часть контракта ([GOTCHAS](GOTCHAS.md) §5).
- **`разрешения.paths`** выдают отдельному дому конкретные каталоги настоящего,
  биндом по тому же пути: `~/.wine` программе Wine, библиотеку Steam — Steam.
  Без этого умолчание «свой дом» ломает ровно те программы, что живут данными в
  общем доме (§3.5).
- **`сеть = ask`** — значение совместимости: сеть спрашивается при каждом
  запуске, как сейчас. Существующие контейнеры мигрируют в него.
- **Основной дом — не контейнер.** «Без контейнера» остаётся (системные
  утилиты, терминал с `sudo`), так и называется и не может держать доверия.

> **Заменено (владелец, 2026-09-26; [PERMISSIONS.md](PERMISSIONS.md) §11.7).**
> Основной дом становится видом дома, `home = main`, любого именованного
> контейнера, а «без контейнера» — встроенным контейнером `main`; `дом` —
> `private | layer | main` (`overlay` читается как `layer`): одно имя — один
> контейнер, какой бы ни был дом, с одним каталогом данных
> (`~/.local/state/vpn-profiles/<имя>/`) и одним — настроек
> (`~/.config/vpn-zones/containers/<имя>/`). Одноразовые виды — разовые
> запуски, не контейнеры. `сеть = ask` — только «ещё не выбрано» (там же,
> §11.8). Доверия у контейнера основного дома по-прежнему нет.

### 3.2 Инварианты

- **I1. Одна сеть в каждый момент; смена — явная.** Контейнер запускается
  только в свою текущую сеть. Смена сети — отдельное действие: «Сменить сеть
  контейнера…» в пикере и GUI, `cellward container set <c> network <сеть>` в
  терминале, опция в Nix — и никогда не побочный эффект выбора, где запустить
  программу. `cellward run <другая> --profile <c>` — отказ с названным выходом,
  а не молчаливый запуск.
- **I2. Работающие программы сохраняют свою сеть.** Процесс нельзя перенести в
  другую сеть (§7). Пока программы контейнера работают в сети A, в сети B он не
  запускается; смена сети предлагает закрыть их и перезапустить.
- **I3. Один контейнер на экземпляр программы.** Реестр пишет селектор;
  проверка конфликта смотрит ещё и на бинарь (сделано).
- **I4. Все слои на любой дороге.** Сеть, дом, разрешения, доверие и
  ограничение композитора накладывает один путь кода (`cellward run` →
  `entry_argv` → `profile-run`) для любого вида сети (сделано для зон,
  `unconfined` и `offline`).
- **I5. Незнакомое — без сети.** Программа без назначения стартует без сети,
  пока её не дали ([GOTCHAS](GOTCHAS.md) §2), в своём доме
  (`defaults.container = own`).
- **I6. Отказ вместо деградации.** Контейнер, чьей сети больше нет, где-то ещё
  не стартует; слой доверия, который не удалось наложить, останавливает запуск
  ([CERTIFICATES.ru.md](CERTIFICATES.ru.md) §4).

### 3.3 Чем может быть сеть

| вид | как | root |
|---|---|---|
| зона: WireGuard/AmneziaWG | ядерный туннель создаётся в аплинке и переезжает в app-ns (сделано) | нет |
| зона: OpenConnect | клиент в аплинке, его tun переезжает в app-ns (сделано) | нет |
| зона: другой клиент (sing-box, OpenVPN, GUI-клиент) | та же схема, M4 | нет |
| через интерфейс хоста | **сделано**: без аплинка — pasta прямо в namespace приложений, её интерфейс называется `awg0`, каждый сокет привязан к этому интерфейсу хоста (`--outbound-if4/-if6`), проброса портов нет; конфиг `[HostInterface]` — второй аплинк, модем, VPN, поднятый системой | нет |
| `unconfined` | сеть хоста, без namespace (сделано) | нет |
| `offline` | только loopback (сделано) | нет |
| **сам** интерфейс хоста внутри контейнера | перенос настоящего линка в чужой netns требует `CAP_NET_ADMIN` в namespace хоста | **да**: маленький системный помощник (опция NixOS-модуля), никогда не по умолчанию |

**Дополнительные маршруты** (`маршруты`) стоят рядом с единственной сетью —
типичный пример LAN рядом с туннелем. Каждый — именованное явное исключение:
правило в аплинке плюс маршрут в app-ns ровно на этот префикс, по умолчанию
выключены и видны в любом отображении контейнера. Второго маршрута по умолчанию
не бывает никогда: два выхода — это утечка, ждущая ошибки маршрутизации.

### 3.4 Объединение двух контейнеров

`cellward container merge <из> <в> [--yes]` и ярлык «Контейнеры cellward»
(`cellward-gui containers`) — **сделано**: для программ, которым оказалось по пути (браузер и менеджер паролей).

- объединяются только контейнеры одного вида: два слоя над домом (их слоты
  оверлея, `<слот>/upper`, сливаются слот за слотом) или два своих дома;
- программы контейнера `<из>` назначаются в `<в>` (`.pinnedprofile`, а заодно
  `.lastprofile` — чтобы пикер не предлагал первым опустевший контейнер);
- дом `<из>` копируется в `<в>` **только там, где у `<в>` такого пути нет**;
  конфликтующие пути уходят в новый каталог `.merged-from-<из>[-N]/` дома `<в>`
  и перечисляются — сливать два профиля браузера инструмент решать не может.
  Ничего не разыменовывается: symlink копируется как symlink, symlink в `<в>` —
  занятое имя, а каталог конфликтов никогда не берётся уже существующий
  (программа из `<в>` могла положить под этим именем ссылку на `~/.ssh`, а
  объединение работает вне песочницы). Сокеты, каналы и пометки удаления
  оверлея пропускаются и считаются;
- сеть остаётся от `<в>`; сертификаты доверия объединяются, и новый для `<в>`
  требует `--yes` — без него объединение отказывает, с ним печатает
  предупреждение ⚠ из [CERTIFICATES.ru.md](CERTIFICATES.ru.md); разрешения и
  выданные пути `<из>` не копируются: у `<в>` остаются свои;
- `<из>` сохраняется, уже без программ, пока его не удалят руками;
- отказ, пока работают программы любого из двух контейнеров (I2), и для
  контейнера, объявленного в Nix (модуль вернул бы его обратно).

### 3.5 Свой дом и его цена

`own` по умолчанию означает, что неназначенная программа стартует в пустом
отдельном доме. Программы, ждущие свои данные в общем доме, их не найдут:

| программа | что ей нужно | как она это получает |
|---|---|---|
| программы Wine | префикс (`~/.wine` или `WINEPREFIX` из ярлыка) | префикс берётся из `Exec` записи и предлагается как `разрешения.paths` при первом запуске |
| Steam | `~/.local/share/Steam`, `~/.steam` | подсказка для известной программы, предлагается при первом запуске |
| программы, которые человек уже настроил в общем доме | их настройки | диалог первого запуска предлагает «свой дом», «слой над домом» (overlay) и «без контейнера» |

Подсказки — список в крейте, где каждая запись называет программу и пути;
ничего не выдаётся без ответа человека.

**Выдача путей — сделано** (подсказки и предложение при первом запуске
остались): `cellward container grant|revoke <имя> <каталог>` и
`containers.<имя>.permissions.paths` в Nix. Программа видит каталог по его
собственному пути, на чтение и запись. Правила:

- **список разрешённого**, а не список опасного: внутри дома или внутри `/mnt`,
  `/media`, `/run/media`, `/srv`. Всё остальное — стены песочницы: в `/run/user`
  сокет D-Bus, который фильтрует прокси, и сокет композитора, в `/tmp` сокеты
  X11, в `/etc` резолвер, который подменяет зона, — и список таких мест рано
  или поздно недосчитается одного сокета;
- никогда весь дом или то, что выше него (это разрешение `home`, которое
  спрашивается словами), и никогда состояние проекта или то, что его содержит:
  в `~/.local/state/vpn-zones` приватные ключи всех зон;
- проверяется как написан **и как разрешён**, при выдаче и заново в
  `fs-sandbox` при каждом запуске: bwrap идёт по symlink, поэтому `~/games`,
  указывающий в состояние, — отказ, а биндится разрешённый каталог. Отвергнутый
  путь пропускается с предупреждением, запуск идёт без него;
- только своему дому: слою над домом и так виден весь настоящий дом.

**Выдача на срок — сделано.** `grant … --for 30m|2h|7d` (не больше 366 дней; в
GUI — час, сутки, неделя) пишет в `paths` песочницы строку
`until=<unix-секунды> <путь>` — старая версия прочтёт её как относительный путь
и откажет. Выдача с истёкшим сроком отсутствует для любого запуска с этой
секунды, убрал её кто-то из файла или нет. Для уже запущенных программ в конце
срока пользовательский таймер зовёт `cellward container expire`, а `revoke`
делает то же сразу: бинд отмонтируется (`umount2(MNT_DETACH)`) в каждом mount
namespace запущенных программ песочницы, куда вход — `setns` владельцем их user
namespace. Отмонтирование не отнимает уже открытое — дескриптор файла, рабочий
каталог внутри; жёсткий конец — `cellward kill`. Каждая выдача, отзыв и
истечение — в журнале (`grant`, `revoke`, `grant-expired`), а
`permissions.paths[].expires` в `status --json` — конец срока (RFC 3339, `null`
без срока).

### 3.6 Устройство одного запуска (порядок — это и есть спецификация)

```
vpn-zone-core wl-sandbox <программа> --zone <зона> --   на хосте: ограниченный сокет Wayland (LEAK-MODEL §13)
[nsenter -U -n -m -t <зона>]  или  [unshare -U --map-current-user --keep-caps]   (unconfined)
  └─ unshare --mount --propagation slave             в зону: каждый контейнер, и основного дома
                                                     (ведомое общего /run/user/<uid> зоны)
      └─ vpn-zone-core profile-run --cwd <каталог> …   (сделано)
           1. дом: слоты оверлея или бинды для разрешения.paths
           2. герметичность runtime (§6, этап 4 — не сделано): tmpfs поверх
              /run/user/<uid>, сокеты возвращаются поимённо; tmpfs поверх
              /tmp/.X11-unix. Покрытие здесь спрятало бы то, что зона
              монтирует в свой runtime позже (общее монтирование, ведомое
              которого — запуск): его надо пропускать или не накрывать runtime
           3. доверие: бинды бандла, базы NSS (CERTIFICATES.ru.md)
           4. chdir <каталог> → $HOME → /          (сделано)
           5. сброс ambient capabilities
           6. exec: fs-sandbox (bwrap) → программа
```

Всё монтируется в собственном mount namespace запуска, никогда — в namespace
зоны: два контейнера одной зоны не должны видеть слоёв и сертификатов друг
друга. bwrap биндит рекурсивно, поэтому песочница видит то, что смонтировали
шаги 1–3.

## 4. Выбор контейнера

Порядок для запуска программы `P`:

1. работающий экземпляр `P` (по id ярлыка) программы, замеченной в передаче
   запуска своей работающей копии: тот же контейнер — клик по такой программе
   означает «разверни окно» ([GOTCHAS](GOTCHAS.md) §11); любую другую
   работающую программу спрашивают, с её сетью и контейнером на выборе;
2. назначение из Nix (`programs.cellward.containers.<c>.apps`);
3. локальное назначение (сделанное в пикере);
4. `defaults.container`: `own` — новый отдельный контейнер с именем программы,
   сеть `offline` и один вопрос: какую сеть ему дать (то же меню, что сейчас,
   ответ запоминается как сеть контейнера).

Пикер показывает контейнер и его сеть и никогда не спрашивает сеть у
назначенной программы:

```
«Firefox» — контейнер firefox · VPN nl · свой дом
  ▶ Запустить
  ⇄ Сменить сеть контейнера…         (I1: явно; работающие программы перезапустятся)
  ⧉ Другой контейнер…                (список контейнеров с их сетями)
  ⊕ Объединить с другим контейнером…
  Разово: одноразовый контейнер, без сети
```

Для контейнеров `ask` и для «без контейнера» сегодняшний диалог «сначала
сеть» остаётся — ничего, на что человек полагается сейчас, не пропадает.

## 5. Запуски мимо лаунчера

Перехват — это **маршрутизация по умолчанию, а не граница безопасности**.
Процесс на хосте всегда может сделать `exec` пути в store напрямую; пользователь
хоста доверенный. Граница проходит в направлении «контейнер → наружу» (§6).

| путь | сегодня | дизайн | этап |
|---|---|---|---|
| ярлык в лаунчере (меню, fuzzel/rofi, KRunner, noctalia) | теневой ярлык пикера в `~/.local/share/applications` | без изменений; пикер «сначала контейнер» | 1 |
| скрытые обработчики (`NoDisplay=true` + `MimeType`) | **сделано**: перехватываются под id видимой записи той же программы | — | 0 |
| записи-дети (`steam steam://rungameid/…`) | **сделано**: без клонов, запуск под id клиента | **сделано**: к ним добавлены веб-приложения браузера (`--app-id=`, `--app=`) | 0/3 |
| записи, которые программы пишут в пользовательский каталог (игры Steam, `userapp-*`, веб-приложения, Wine) | не перехватываются: чужие файлы не переписываются | **сделано**: перехват на месте с резервной копией и повторный перехват после перезаписи ([LAUNCHERS.ru.md](LAUNCHERS.ru.md) §3.2); инвариант изменён отдельным коммитом | 3 |
| `xdg-open`, `gio open`, `kde-open`, «открыть с помощью» | находят `.desktop` → теневой ярлык | без изменений | — |
| D-Bus-активация (`gapplication launch`, `DBusActivatable=true`) | service-файл активирует мимо тени | **сделано** (§5.3): теневые сессионные service-файлы в `$XDG_DATA_HOME/dbus-1/services/<id>.service` только для перехваченных id; никогда для порталов и системных имён | 3 |
| автозапуск XDG | стартует без контейнера | **сделано** (§5.2): назначенные программы стартуют в своём контейнере; **неназначенным при входе показывается пикер** (`ask`, с 2026-09-24), а при `offline` или без экрана — без сети, в своём доме, с уведомлением | 3 |
| бинды композитора | только если бинд зовёт `vpn-zone-pick` | **сделано** (§5.1): `cellward launch <id-ярлыка>` берёт `Exec` из записи и идёт через пикер | 3 |
| шелл | без контейнера | **сделано**: по желанию — PATH-шимы для назначенных программ (`pathShims.enable`); границей не являются | 3 |
| портал `OpenURI` из программы хоста | портал → запись обработчика → тень → пикер | без изменений | — |
| портал `OpenURI` из контейнера | происхождение теряется | брокер (§6.2) | 4 |
| ссылка, открытая изнутри зоны | делегируется через `systemd --user` | та же дверь, но с охраной: брокер | 4 |
| `systemd-run --user`, `systemctl --user` изнутри зоны | доступны | герметичность runtime (§6.1) | 4 |
| `flatpak-spawn --host` | выходит через сессионную шину | у отдельных домов шина уже отфильтрована; оверлеи — с §6.1 | 4 |
| программы, запущенные другими программами хоста | без контейнера | вне рамок (хост доверенный); `doctor` это называет | — |

### 5.1 Команда запуска для биндов

`cellward launch <id-ярлыка> [-- доп. аргументы]` — **сделано** — находит
запись по id в тех же каталогах, что читает `sync`, берёт её `Exec` (коды
полей — из доп. аргументов) и становится пикером для неё:

```kdl
Mod+B { spawn "cellward" "launch" "firefox"; }
```

- запись берётся программы, а не наша: перехваченная на месте читается из
  резервной копии, а наша запись пикера пропускается ради оригинала, который
  она затеняет дальше по списку, — бинд никогда не заворачивает пикер в пикер;
- коды полей заполняются так, как их заполняет лаунчер: `%u`/`%f` — первый
  аргумент, `%U`/`%F` — все, `%i` → `--icon <Icon>`, `%c` — имя, `%k` — файл
  записи, `%%` — знак процента, устаревшие коды выбрасываются. Аргументы, для
  которых в записи нет кода, не передаются, и об этом говорится;
- наши служебные `vpn-zone-*` — отказ: они запускают GUI, а не программу;
- `VPN_ZONE_DRYRUN=1` печатает команду пикера вместо запуска — проверить бинд;
- шеллы дополняют id, которые знает пикер (`.labels`).

Бинд, зовущий программу напрямую, по-прежнему запускает её без контейнера:
композитор — программа хоста, а хосту доверяем (§5). Меняется то, что путь в
контейнер стал на одно слово длиннее, а не скриптом.

### 5.2 Автозапуск

Пользовательские `~/.config/autostart/*.desktop` перехватываются на месте тем
же проходом и по тем же правилам, что пользовательские записи ярлыков: только
обычные файлы; байты оригинала сначала кладутся в
`~/.local/state/vpn-zones/.adopted-autostart/`; запись перехватывается заново,
когда программа её переписала; возвращаются через
`autostart.unassigned = "as-is"` или `cellward mode off`. Новый `Exec` —
`vpn-zone-pick --autostart --id <ключ> -- <исходная команда>`.

- **Ключ** — тот, под которым лежат закрепления программы, а не имя файла:
  файлы автозапуска называет тот, кто их пишет (`telegramdesktop.desktop` рядом
  с `org.telegram.desktop.desktop`). По порядку: `--id` скопированной записи
  пикера; запись ярлыка с тем же именем файла; запись той же программы; имя
  файла.
- **Выбранное стартует без вопроса** и с `--autostart`. Программа уже
  работает — туда, где работает. Контейнер: закреплённый или назначенный,
  иначе общий контейнер по умолчанию, если это ответ (`main`, `own`,
  существующий контейнер). Сеть: к которой привязан этот контейнер, иначе
  закреплённая.
- **Невыбранное** — по `autostart.unassigned`. `ask` (по умолчанию с
  2026-09-24, решение владельца): тот же пикер, что при щелчке, с «всегда» —
  программа спрашивается один раз, при первом входе, а не запускается в пустой
  свой дом, где у неё нет данных (KeePassXC владельца 24.09: без базы и без
  темы). `offline` (по умолчанию 17–24.09) и `ask` без экрана: свой дом и
  `offline`; прошлый выбор и общая сеть по умолчанию НЕ берутся — это то, что
  диалог выделяет, а не согласие выйти в сеть без вопроса; ничего не
  запоминается, что угадано — сообщает уведомление.
- **Диалога доступов тоже нет**: своему дому, который ещё ни разу не
  запускался, кладётся пустой файл доступов — тот ответ, что даётся, когда
  спросить негде.
- **Не трогаются**: symlink (`xdg.autostart` home-manager); записи, которые
  ничего не запускают (`Hidden=true`, `X-GNOME-Autostart-enabled=false`, нет
  `Exec`); скопированный клон зоны (он сам называет сеть); `/etc/xdg/autostart`
  целиком — это компоненты рабочего стола, а запись с тем же именем в
  пользовательском каталоге переопределила бы, то есть выключила, их.
  Скопированная запись пикера разворачивается, а не оборачивается второй раз.
- path-юнит следит за `~/.config/autostart`: программа, включившая себе
  автозапуск, перехватывается сразу, задолго до следующего входа.

### 5.3 D-Bus-активация

Программу с `DBusActivatable=true` запускает сессионная шина, когда кто-то
обращается к её имени, — `gapplication launch`, действие уведомления, «открыть
с помощью» файлового менеджера, другая программа, — и шина читает **service-файл**
программы, а не её ярлык. `DBusActivatable=false` в наших ярлыках помогает
только лаунчерам, которые его уважают. Поэтому `sync` для каждой перехваченной
записи (тень пикера или перехват на месте) с `DBusActivatable=true` пишет
теневой сервис с тем же именем в `~/.local/share/dbus-1/services/`:

```ini
# X-VPNZone=dbus
[D-BUS Service]
Name=org.example.Notes
Exec=<пикер> --id org.example.Notes -- <Exec исходного сервиса>
```

- сессионная шина читает каталог пользователя первым, а более поздний файл с
  тем же именем пропускает; `SystemdService=` оригинала отбрасывается, иначе
  шина запустила бы этот юнит вместо `Exec`;
- только имена перехваченных записей и только корректные имена шины: для
  портала, системного компонента или имени без ярлыка не пишется ничего.
  Service-файл пользователя с тем же именем не перезаписывается никогда; наши
  убираются, когда запись перестаёт перехватываться (`mode off`);
- dbus-broker не следит за своими каталогами сервисов: если тень изменилась,
  `sync` просит `systemctl --user --no-block reload dbus.service`;
- уже запущенная программа владеет своим именем, и шина отдаёт вызовы ей — в
  той сети, где она запущена, как щелчок по запущенной программе.

## 6. Граница наружу (этап 4)

Это пункты M3; контейнеры превращают их в умолчания контейнера.

### 6.1 Герметичность runtime

В mount namespace запуска: tmpfs поверх `/run/user/<uid>`, назад биндами —
только сокет Wayland (уже ограниченный), PipeWire, PulseAudio и сокет брокера;
tmpfs поверх `/tmp/.X11-unix` плюс `unset DISPLAY` ([LEAK-MODEL](LEAK-MODEL.md)
§7), а программам с разрешением `x11` — свой `xwayland-satellite` контейнера;
по выбору tmpfs поверх `/run/dbus`. Отдельные дома всё это уже получают через
bwrap; оверлеи — когда появится брокер.

### 6.2 Брокер

По сокету на контейнер, в его runtime-каталоге. Один глагол: «открой это» (URI,
файл, переданный дескриптором, или id ярлыка). Сторона хоста знает
контейнер-источник:

- программа назначена **тому же** контейнеру → запуск там же, без диалога;
- контейнер заперт → только тот же контейнер;
- иначе → пикер, с источником в вопросе.

Входы изнутри контейнера: `xdg-open`/`$BROWSER` указывают на клиента брокера;
делегирование в `launch.rs` (шаг 1) идёт в брокер; порталы перестают получать
`OpenURI`/`OpenFile` через прокси шины (правила `--call` по интерфейсам
порталов). GTK, Qt и Firefox под `/.flatpak-info` зовут портал и на `xdg-open`
не откатываются, поэтому сначала нужен совместимый с порталом фронт для
`OpenURI`. **Открытый вопрос исследования**, прототип в VM прежде любых
обещаний.

## 7. Границы возможного без root

- **Нет глобального перехвата `exec`.** События разрешений fanotify, хуки LSM и
  eBPF требуют `CAP_SYS_ADMIN`/`CAP_BPF` в исходном user namespace. seccomp
  user notification потребовал бы `NO_NEW_PRIVS` на всю сессию, что ломает все
  setuid-помощники (`sudo` и `newuidmap`, на котором стоят зоны), и всё равно не
  достаёт до детей `systemd --user`.
- **Нет сетевой политики по процессам на хосте.** cgroup BPF и `net_cls`
  требуют root. Сеть — это всегда namespace.
- **Работающий процесс нельзя перенести** в другую сеть или контейнер; `setns`
  действует на вызывающего (I2).
- **Интерфейс хоста нельзя перенести в контейнер** без `CAP_NET_ADMIN` в
  сетевом namespace хоста (§3.3). Трафик *через* него — можно без root; *сам*
  интерфейс внутри — только системным помощником.
- **Файлы хоста не меняются — меняется только их вид**, а точка монтирования
  обязана уже существовать: внутри каталогов root ничего не создать.
- **Сессионную шину хоста нельзя отфильтровать для программ хоста** — только
  для контейнеров, через прокси.
- **Модули ядра** (`amneziawg`, `nf_tables`) из user namespace не грузятся, а
  `/etc/subuid` один раз требует администратора.
- **Программам со встроенным доверием или своим runtime** (Flatpak,
  pressure-vessel Steam, AppImage, `webpki-roots`) слой доверия снаружи не дать
  ([CERTIFICATES.ru.md](CERTIFICATES.ru.md) §2).
- **Записи в собственном каталоге приложений пользователя** перехватываются
  только перезаписью, и программа, переписывающая свою запись, выигрывает на
  мгновение — до повторного перехвата ([LAUNCHERS.ru.md](LAUNCHERS.ru.md) §3.2).

## 8. Декларативная конфигурация (опции home-manager-модуля)

Опции принадлежат **home-manager**-модулю (`homeModules.default`) и задаются в
домашней конфигурации того пользователя, к которому относятся; в NixOS-модуле
их нет (его `programs.cellward.enable` только добавляет home-manager-модуль каждому
пользователю home-manager, с `programs.cellward.enable` по умолчанию). Прежде опции
назывались `programs.vpn-zones.*`; старые имена работают, с предупреждением.
Декларативные значения пишутся в `~/.config/vpn-zones/declared/` этого
пользователя (ссылки в store, только чтение) и сильнее локального состояния;
CLI и GUI показывают их как «задано в Nix» и отказываются менять.

```nix
programs.cellward = {
  enable = true;

  launcher.mode = "picker";              # picker | per-zone (устарел) | both (устарел) | off
  defaults = {
    network = "offline";                 # offline | unconfined | <зона>
    container = "own";                   # own | ask | main | <контейнер>
  };
  compositorRestriction.enable = true;
  hermetic.default = true;               # и hermetic.exceptions = [ "<зона>" ]
  zoneX11 = [ ];                         # зоны, чьим программам — свой X-сервер

  containers.work = {
    home = "private";                    # private | overlay
    network = "nl";                      # <зона> | unconfined | offline | ask
    apps = [ "firefox" "org.telegram.desktop" ];
    permissions = {
      paths = [ ];                       # напр. [ "~/.wine" ] — только своему дому
      x11 = false;
    };
    trust = {                            # CERTIFICATES.ru.md
      certificates = [ ./certs/some-root-ca.pem ];
      acknowledgeRisk = true;            # обязательно, если certificates не пуст
    };
  };

  autostart.unassigned = "ask";          # ask (по умолчанию) | offline | as-is
  interception.userEntries = "take-over";  # take-over | leave — LAUNCHERS.ru.md §3.2
  desktop = {                            # клавиша меню окна и правило наших окон
    windowMenu.key = null;               # напр. "Mod+Shift+V", запись niri
    niri.enable = false;
    sway.enable = false;
  };
};
```

Зона через интерфейс хоста — такая же зона, из файла `[HostInterface]` через
`cellward add`, не опция. Именованных дополнительных маршрутов рядом с сетью и
готовых наборов каталогов (`downloads`, `documents`) нет: своему дому выдаётся
`permissions.paths`.

- Сами зоны не декларируются: конфиг зоны — это приватный ключ, в Nix store ему
  не место никогда. Декларативный контейнер, названный на несуществующую сеть, —
  отказ при запуске (I6), а не ошибка вычисления.
- Проверки: непустой `trust.certificates` требует `acknowledgeRisk`; одна
  программа в `apps` двух контейнеров — ошибка; `permissions.paths` у дома
  `overlay` — ошибка (не применяется), как и путь, который не абсолютный и не
  `~/…`.

## 9. Машиночитаемое состояние

`cellward container show <имя> --json` — подмножества той же схемы.

- **`schema_version`** есть в каждом документе. В пределах версии изменения
  только добавляющие; удаление поля или смена его смысла — новая версия и запись
  в CHANGELOG.
- **У каждого настраиваемого значения указано происхождение**: `{"value": …,
  "source": "nix" | "local" | "default"}`. Факты времени выполнения (`running`,

**Ключи для сопоставления — часть контракта версии 1:**

- контейнер определяется **`selector`**, а не `name`: у слоя над домом и у
  своего дома могло быть одно имя (`work` и `sb:work` были двумя разными
  контейнерами). Любая ссылка на контейнер в документе —
  `apps[].container.value` — это селектор, и сопоставляется он с
  `containers[].selector`. С одним именем на контейнер (2026-09-26,
  [PERMISSIONS.md](PERMISSIONS.md) §11.7) селектор И ЕСТЬ имя — `sb:` больше
  не пишется, — а у `home` есть значение `main` для контейнера настоящего
  дома (слой по-прежнему `overlay`). **Незнакомое значение `home` читатель
  обязан считать «без изоляции»**: `main` — весь настоящий дом, и инструмент,
  показавший незнакомый вид как свой дом, показал бы настоящий дом
  изолированным;
- сеть — по `name`; `networks[].kind` — одно из `unconfined`, `offline`,
  `wireguard`, `openconnect`, `host-interface`, `system-zone`, а `interface` —
  интерфейс хоста для `host-interface` и `null` для всех остальных; сеть
  `host-interface` этим проектом НЕ шифруется; `system_zone` — системная зона,
  через туннель которой выходит сеть `system-zone` (`docs/SYSTEM.md` §7b), и
  `null` для всех остальных (добавлен в 2026-09 как дополнительный ключ: для
  читателей, пропускающих незнакомые ключи, версия 1 не меняется);
- `networks[].aliases` — другие имена, по которым сеть читается. Такое одно:
  `direct` у `unconfined`, её имя до 2026-09. Оно принимается в CLI, в Nix
  (`defaults.network`, `containers.<n>.network`), в закреплениях и настройках,
  записанных до переименования, и нигде в документе не встречается как
  значение — все `network.value` и `apps[].network.value` говорят
  `unconfined`;
- программа — по ключу ярлыка (`apps[].id`, `containers[].apps[].value`), это
  ключ без потерь из `docs/LAUNCHERS.ru.md` §3.4.

**`uplink_owner`** (`{uid, gid}` или `null`) — для политики хоста на выход:
каждый сокет, которым трафик зоны покидает хост, — pasta и клиента
OpenConnect, — принадлежит uid 0 зоны, началу подчинённых диапазонов
пользователя, поэтому `meta skuid <uid>` в nftables хоста выпускает зоны и
больше ничего от этого пользователя. Стабильно, пока стабилен `/etc/subuid`;
учти, что rootless-контейнерный инструмент, отображающий свой uid 1 на тот же
подчинённый uid, тоже подойдёт под правило.

## 10. Куда теперь может уйти пакет или DNS-запрос мимо туннеля?

- **Меняемые сети (I1, I2).** Смена явная и видимая; контейнер никогда не
  работает в двух сетях сразу. Канал личности из [LEAK-MODEL](LEAK-MODEL.md) §4
  сужен до сознательного действия.
- **Сети через интерфейс хоста** (сделано). pasta в app-ns привязывает каждый
  сокет к одному интерфейсу хоста; app-ns — тот же двухлинковый namespace (`lo`
  и `awg0`), что и для туннеля, с тем же фаерволлом, поэтому изнутри другой
  выход не выбрать, а упавший интерфейс — это отсутствие сети, а не обход.
  Проброса портов в pasta нет. Чего такая сеть не делает — не шифрует; так она
  и называется везде, где показана (`host-interface`).
- **Дополнительные маршруты.** Каждый — дыра по определению: явная, по
  префиксу, выключена по умолчанию, видна в любом отображении и в `doctor`.
- **Контейнеры в `unconfined`** (сделано). Сетевого namespace нет — сеть и резолверы
  хоста, и так и названо. User namespace прав над netns хоста не даёт.
- **Mount namespace запуска, выдача путей.** Сеть не меняется. Выданный
  каталог — канал данных между контейнером и всем, что видит тот же каталог:
  сознательный, виден в `container show` и в JSON. Список разрешённого не даёт
  ему стать каналом к службе хоста: каталог с сокетами (`/run`, `/tmp`) выдать
  нельзя, поэтому ни нефильтрованный D-Bus, ни X11 или резолвер хоста через
  выдачу не достать.
- **Тени D-Bus** (сделано) закрывают путь: активация программы по имени на
  шине запускала её в сети хоста и без контейнера.
- **Автозапуск** (сделано) закрывает путь: программа, включившая себе
  автозапуск, стартовала при входе в сети хоста и без контейнера; теперь — туда,
  куда её поместили, или без сети. Нового сокета и маршрута не появляется.
- **`cellward launch`, шимы, тени автозапуска и D-Bus, перехваченные записи.**
  Только запускают пикер или `cellward run`; ни нового сокета, ни маршрута.
- **Брокер.** Дверь с охраной вместо неохраняемого пути через `systemd --user`.
- **Вывод JSON.** Называет зоны и контейнеры процессам пользователя; внутри
  отдельного дома каталога состояния не видно вовсе.
- **Слой доверия.** Канал MITM со своим разбором:
  [CERTIFICATES.ru.md](CERTIFICATES.ru.md) §5.
