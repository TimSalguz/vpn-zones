# GOTCHAS — накопленные грабли cellward (прежде vpn-zones)

Это спецификация накопленного поведения проекта: систематическая выгрузка всех неочевидных фактов («граблей») из комментариев и кода `module/default.nix` и крейта `rust/` — для переписывания ядра на Rust. Каждая запись должна превратиться либо в тест, либо в явно сохранённый инвариант нового кода: ни одна не должна потеряться.

Ссылки на файлы — где грабля живёт СЕЙЧАС. Что уже переехало в Rust: жизненный цикл зоны (`rust/src/zone.rs`, бывшие shell-скрипты `zoneHolder` и `zoneInit` из `module/default.nix`), слои контейнеров данных (`rust/src/profile.rs`, бывший `module/vpn-profile-run.py`), генератор ярлыков (`rust/src/desktop.rs`, бывший `module/vpn-zone-sync.py`), ограничитель доступа к композитору (`rust/src/wl_sandbox.rs`, бывшая программа на C `module/wl-sandbox.c`), песочница файловой системы (`rust/src/fs_sandbox.rs`, бывший shell-скрипт `vpn-fs-sandbox` из `module/default.nix`), сам CLI (`rust/src/cli.rs` + `rust/src/launch.rs` + `rust/src/registry.rs`, бывший `writeShellScriptBin vpn-zone` оттуда же), пикер сети (`rust/src/picker.rs`, бывший `writeShellScriptBin vpn-zone-pick`), шесть GUI-ярлыков (`rust/src/gui.rs` + общий `rust/src/dialog.rs`, бывшие шесть `writeShellScriptBin *-gui`), разбор конфигов (`rust/src/config.rs`) и seccomp-фильтр (`rust/src/seccomp.rs`). Логики на shell не осталось: в модуле три двухстрочные обёртки, назначающие `VPN_ZONE_TOOLS`. Каждая грабля этих файлов закрыта юнит-тестом рядом с кодом — кроме тех, что требуют живого композитора: они проверяются руками на niri/KWin, а тестами закрыты fallback-пути.

## 1. User namespaces и capabilities

- **Двойной маппинг uid: иначе либо нет capabilities, либо чужой uid.** Внутри зоны нужен uid 0 — capabilities теряются при execve, если uid ненулевой (проверено: с identity-маппингом CapEff=0), и ядро не даёт создать интерфейс. Второй диапазон (`--map-users=<uid>:<uid>:1`) отображает настоящий uid в себя, чтобы приложение, вошедшее через `nsenter --preserve-credentials`, работало под твоим uid и видело $HOME — ровно как podman в режиме keep-id. (`rust/src/zone.rs`; обзор — в шапке `module/default.nix`)

- **subuid — источник «root» зоны.** uid 0 внутри берётся из первого диапазона /etc/subuid (newuidmap имеет на это cap_setuid). Нет диапазона — rootless-зона невозможна в принципе; это проверяется явно с внятной ошибкой. Сами newuidmap/newgidmap ищутся ПО PATH, а не по абсолютному пути: это setuid-обёртки, на NixOS они в /run/wrappers/bin, в Debian-подобном CI — в /usr/bin. (`rust/src/zone.rs`)

- **Из namespace нельзя перейти в другой namespace.** Процесс, уже находящийся в user+net namespace, не может войти в другой: «nsenter: reassociate to namespaces failed». Симптом: клик по ссылке в Telegram-в-зоне открывал пикер, а браузер не появлялся вовсе, причём «Прямой интернет» молча наследовал сеть зоны. Решение — делегировать запуск наружу (см. раздел systemd). Следствие для запертой зоны (lock/no-escape): повторно войти даже в СВОЮ зону нельзя — аргументы выбора сети/профиля отбрасываются и команда исполняется на месте через exec; профиль отбрасывается тоже, потому что прав смонтировать слой внутри зоны уже нет. (`rust/src/launch.rs`)

- **`nsenter --keep-caps` обязателен для монтирования профиля.** Без него CapEff обнуляется при входе в user namespace зоны, и смонтировать overlay-слой нечем. (`rust/src/launch.rs`)

- **`nsenter`, входя в mount namespace, делает `chdir("/")` — рабочий каталог восстанавливает `profile-run`, ПОСЛЕ монтирования.** Старый cwd принадлежит другому namespace, и терминал, запущенный в зоне, открывался в корне (воспроизведено на живой машине 2026-08-30). Флаг `nsenter --wd` не лечит: с контейнером overlay монтируется поверх `$HOME` уже после `nsenter`, и ранний chdir залип бы на каталоге ПОД слоем — шелл сидел бы в нижнем слое, не видя своих файлов; а без контейнера каталог, которого нет в дереве монтирования зоны (оно — частная копия на момент подъёма; флешка, примонтированная позже, туда не попадает), заставил бы `nsenter` вовсе отказаться запускать программу. Поэтому ВСЕ запуски, входящие в namespace, кончаются `vpn-zone-core profile-run --cwd <каталог вызывающего>` (для основного профиля — с пустым каталогом слоя, то есть без монтирований): chdir после монтирования, откат на `$HOME`, затем на `/`. `direct` без контейнера namespace не меняет, и cwd переживает exec сам. Смоук проверяет обе половины: `pwd` в зоне и относительный путь к файлу, лежащему ТОЛЬКО в верхнем слое. (`rust/src/launch.rs` `entry_argv`, `rust/src/profile.rs` `start_dirs`)

- **mount(8) не работает без root даже при CAP_SYS_ADMIN.** Утилита из util-linux при запуске не от root пытается сбросить привилегии и падает с «drop permissions failed», хотя права на монтирование есть (получены от nsenter --keep-caps). Прямой вызов libc.mount такой проверки не делает — монтировать надо системным вызовом. (`rust/src/profile.rs`)

- **Ambient capabilities переживают execve — чистить явно.** Без `prctl(PR_CAP_AMBIENT, PR_CAP_AMBIENT_CLEAR_ALL)` перед запуском Chrome унаследовал бы CAP_SYS_ADMIN внутри namespace. Права нужны ровно на монтирование, дальше снимаются. (`rust/src/profile.rs`)

## 2. Сеть, маршрутизация, pasta

- **Зона — ДВА netns, и сокет туннеля остаётся в том, где интерфейс родился.** Ключевое свойство ядерного WireGuard/AmneziaWG: UDP-сокет живёт в namespace, где интерфейс был **создан**, и при `ip link set … netns …` не переезжает вместе с ним. На этом стоит вся шлюзовая архитектура (`docs/LEAK-MODEL.md`): awg0 создаётся в uplink-ns (там pasta и вся связность) и переезжает в app-ns, где, кроме него и lo, нет ничего. Порядок обязателен: сначала создать наверху, потом переехать, и только потом `setconf`/адреса/MTU/маршруты — netlink работает по ТЕКУЩЕМУ netns, так что настраивать надо уже внизу. Оттуда же (из app-ns) пишется зеркало состояния: `awg show` читает интерфейс по текущему netns. (`rust/src/zone.rs`, `uplink_setup`/`zone_setup`)

- **Endpoint резолвится ЗАРАНЕЕ, в host-netns, и подставляется литералом.** `wg setconf` резолвит `Endpoint` сам, через `getaddrinfo`, и при неудаче ретраит по нарастающей ~90 секунд. В app-ns сети нет до самого туннеля, который этот setconf и настраивает, — с хостнеймом в конфиге зона зависла бы и потом всё равно упала. Поэтому держатель резолвит все Endpoint'ы ещё до форков (метод `WgConfig::resolve_endpoints`) и пишет в текст для setconf литеральные адреса; v6 — в скобках и только при наличии порта (`[fd00::1]:51820`), без порта скобки недопустимы. Нерезолвящееся имя — фатальная ошибка с внятным текстом, а не молчаливое зависание. (`rust/src/config.rs` `resolve_endpoints`, `rust/src/zone.rs` `prepare`)

- **Маршрута «до endpoint мимо туннеля» больше НЕТ, и это не регресс.** В одно-namespace модели он был обязателен (иначе пакеты туннеля заворачивались бы в туннель), но был виден и приложениям — /32 до VPN-сервера мимо VPN. В шлюзовой архитектуре шифрованный трафик рождается в uplink-ns и уходит ЕГО default-маршрутом, а в app-ns исключений нет вовсе: `ip route get <endpoint>` там обязан вести в awg0. Смоук проверяет именно перевёрнутое условие — если однажды маршрут «мимо» вернётся, тест покраснеет. (`rust/src/zone.rs`, `tests/integration/smoke.sh`)

- **Killswitch держится на том, что uplink-ns умирает.** Приложения держат app-ns живым и после смерти держателя, но uplink-ns не держит никто — ядро его уничтожает, а WireGuard на исчезновение своего «родного» namespace гасит carrier и закрывает сокеты (`wg_netns_pre_exit`). awg0 в app-ns остаётся на месте и дропает всё: fail-closed без единого правила фаерволла. Держатель со своей стороны супервизит ОБА процесса — умер любой, гасятся оба и pasta. (`rust/src/zone.rs`, `supervise`)

- **Синхронизация трёх процессов — на трубах, не на таймаутах.** Порядок вынужденный: app-ns форкается первым (аплинку нужен его pid для `ip link set … netns <pid>`), аплинк сообщает о своём namespace держателю (только после этого есть к чему цеплять pasta), app-ns сообщает о себе аплинку (только после этого есть куда переезжать), аплинк отдаёт вниз байт «переехало» — заодно и то, какой из двух модулей получился (amneziawg или ядерный wireguard), потому что интерфейс создаёт он. Смысл труб именно в EOF: умерший процесс закрывает свой конец, и другая сторона получает ошибку сразу, а не через таймаут. Каждый конец надо закрывать у тех, кому он не нужен, иначе EOF не наступит никогда. (`rust/src/zone.rs`, `supervise`)

- **pasta цепляется к АПЛИНКУ (`uplink.pid`), а не к зоне приложений.** Файл `zone.pid` остаётся контрактом наружу и по-прежнему указывает на namespace приложений — по нему ходит `nsenter` из `cellward run`/`status`. `cellward gc` находит осиротевшую pasta по номеру из её же командной строки (`/proc/N/ns/net`) — теперь это номер аплинка, и проверка живости работает без изменений. (`rust/src/zone.rs`; `rust/src/cli.rs` gc)

- **У pasta по умолчанию открыты четыре двери, и аплинку не нужна ни одна.** `-t auto`/`-u auto` отражают каждый порт, занятый в namespace, на ХОСТЕ и пробрасывают внутрь: UDP-сокет туннеля получал порт на всех адресах машины, видимый из локальной сети. `-T auto`/`-U auto` отражают порты, занятые на loopback хоста, на loopback аплинка, а фаерволл аплинка `lo` пропускает — клиент OpenConnect в аплинке мог бы говорить с любой локальной службой хоста. Ещё адрес шлюза отображается на loopback хоста. Туннелю всё это не нужно: его пакеты — потоки, которые он начинает сам, и pasta отслеживает их без всякого проброса. Поэтому `-t none -u none -T none -U none --no-map-gw`; флаги дописаны ПОСЛЕ `--netns /proc/N/ns/net`, чтобы шаблон смоук-теста и разбор `gc` не сломались. Проверено VM-тестом с настоящим WireGuard-пиром. (`rust/src/zone.rs` `PASTA_CLOSED`)

- **Зона через интерфейс хоста: pasta в namespace приложений, свой адрес, привязка — не маршрутизация.** Аплинка нет: pasta цепляется прямо к app-ns, называет свой интерфейс `awg0` (фаерволл, `doctor` и `check` знают одно имя) и привязывает каждый сокет на хосте к выбранному интерфейсу (`--outbound-if4/-if6`, то есть `SO_BINDTODEVICE`): пакет уходит через него или никуда, таблица маршрутов хоста не решает ничего — VM-тест проверяет, что зона, привязанная к другому интерфейсу, не достаёт до сети eth1. Адрес зоне дан свой, `10.255.255.253/30` со шлюзом `.254`: pasta берёт адрес и шлюз из МАРШРУТА ПО УМОЛЧАНИЮ интерфейса, а у интерфейсов, ради которых такая зона нужна (соседняя LAN, системный VPN с отдельной таблицей), его часто нет — и pasta тогда молча отказывается от IPv4 целиком. pasta транслирует сокеты, а не адреса, так что другая сторона всё равно видит адрес интерфейса хоста. IPv6 — либо привязан к интерфейсу (`--outbound-if6`), либо выключен в зоне целиком (`-4`), и никогда не «включён, но не привязан»: тогда он ушёл бы по маршруту хоста через другой интерфейс. Привязывается, только если у интерфейса есть глобальный IPv6-адрес и маршрут по умолчанию через него, — иначе pasta отказывается стартовать вовсе («External interface not usable»). Интерфейс проверяется при подъёме, в сети хоста: его нет — зона не поднимается, а не делает вид. (`rust/src/zone.rs` `supervise`, `HOSTIF_GUEST4`; `rust/src/hostif.rs`)

- **Собственный адрес хоста ИЗ ЗОНЫ НЕ ВИДЕН — pasta его копирует.** `pasta --config-net` переносит в namespace адрес, MTU и маршруты выходного интерфейса хоста: у аплинка на `hostif` ровно тот же `10.x.x.x`, что у машины на `eth0`. Поэтому соединение из зоны «на адрес хоста» уходит не наружу, а в собственный стек namespace и получает `Connection refused` (поймано в CI, когда тестовый ocserv слушал на адресе раннера). Практическое следствие для тестов: сервер, до которого зона должна дойти «как до интернета», обязан иметь ОТДЕЛЬНЫЙ адрес — например из TEST-NET-1 на `lo` хоста: в namespace такого адреса нет, пакет уходит маршрутом по умолчанию в pasta, а pasta открывает соединение уже в сети хоста, где адрес локальный. (`tests/integration/smoke.sh`, часть про OpenConnect)

- **pasta: `-I hostif` против столкновения имён.** По умолчанию pasta копирует имя выходного интерфейса хоста; если хост сам под VPN и интерфейс называется awg0, внутри зоны случилось бы столкновение имён с туннелем зоны. Имя задаётся явно. (`rust/src/zone.rs`)

- **Namespace — отдельный форкнутый процесс, чтобы pasta могла подключиться.** pasta остаётся в сети хоста и цепляется снаружи по `--netns /proc/<pid>/ns/net`, поэтому net+mount namespace создаётся отдельным процессом (`unshare --net --mount --fork`), а не в том же, где pasta. (`rust/src/zone.rs`)

- **Переезд интерфейса между namespace требует прав в ОБОИХ.** Работает потому, что оба netns созданы процессами одного user namespace, а мы в нём uid 0: CAP_NET_ADMIN над namespace даёт власть в userns-владельце. По той же причине приложение, вошедшее в app-ns без capabilities, ни добавить интерфейс, ни вернуть маршрут не может — его собственный вложенный userns даёт права только над его новыми пустыми namespace. И pid для `ip link set … netns <pid>` — ХОСТОВЫЙ: pid namespace не создаётся нигде, ни для этого, ни для pasta, ни для nsenter. (`rust/src/zone.rs`)

- **Маршрут pasta разбирается по ключевым словам, не по позициям.** У pasta default-маршрут имеет вид «default dev hostif scope link» (без via), у обычной сети — «default via 192.168.1.1 dev enp4s0 …». Позиционный разбор во втором случае ловил слово «link» вместо имени интерфейса (проверено). Разбор остался и в шлюзовой архитектуре: аплинк ждёт, пока pasta вообще создаст default-маршрут, и по наличию `dev` отличает «pasta не подключилась» от «подключилась, но настроила иначе» — туннель создаётся только после этого, иначе его пакетам некуда идти. (`rust/src/zone.rs`, `parse_default_route`)

- **Историческое: маршрут до VPN-сервера мимо туннеля.** В одно-namespace модели он был обязателен (иначе петля: пакеты туннеля заворачиваются в туннель), но именно он и был дырой — приложения видели /32 до сервера и весь интерфейс pasta. С переходом на шлюзовую архитектуру блок удалён целиком, вместе с ним ушла и вся v6-специфика endpoint'а (транспорт живёт в uplink-ns, его семейство app-ns не касается). Возврат этого маршрута в app-ns — регресс герметичности; смоук проверяет обратное условие. (`rust/src/zone.rs`, `tests/integration/smoke.sh`)

- **`ip route`: ТИП идёт ПЕРЕД префиксом.** `ip -6 route replace default unreachable` — не маршрут, а синтаксическая ошибка: iproute2 разбирает «default» как префикс, потом видит тип маршрута, за которым ничего нет, и выходит с «Command line is not complete» (проверено, код 255). Правильно — `ip -6 route replace unreachable default`. В одно-namespace версии слова стояли в неверном порядке, то есть v6-фолбэк «закрыть default» не работал ни разу; не заметили потому, что до него обычно выигрывала ветка с sysctl `disable_ipv6`. (`rust/src/zone.rs`)

- **Оффлайн-зона: отсутствие маршрута вместо запрета.** Особая зона — только loopback, без туннеля, без аплинка и без pasta: программа работает, но маршрута наружу физически не существует. Это основа политики «интернет не выдаётся, пока его явно не дали». Такая зона — пустой namespace, создаётся по требованию и в конфиге не хранится; `unconfined` (прежде `direct`) и `offline` — встроенные варианты пикера, а не зоны, их нельзя удалить и они не показываются в GUI удаления. (`rust/src/zone.rs`; `rust/src/cli.rs` rm; `rust/src/gui.rs` remove)

- **Один приватный ключ нельзя поднимать дважды.** Сервер помнит для ключа ровно один endpoint, второе соединение перебивает первое — оба начинают рваться. Нельзя поднимать зону из конфига, уже поднятого системным туннелем, и нельзя делить один файл между двумя зонами: нужны разные ключи. (`module/default.nix`, шапка)

- **Kill switch = процессы-держатели + KillMode + топология.** Каждый namespace живёт, пока жив припаркованный на `pause()` процесс: умер процесс app-ns — исчезла зона и сеть у всего, что в ней работало; умер аплинк — у туннеля закрылся транспортный сокет. На уровне systemd KillMode=control-group (по умолчанию) гасит вместе с зоной и pasta, и всё запущенное внутри; сам держатель передаёт TERM/INT обоим и pasta, чтобы ничто не пережило его при запуске без systemd. (`rust/src/zone.rs` + юнит vpn-zone@ в `module/default.nix`)

- **gc — точные критерии, а не «убить всё осиротевшее».** Первая версия gc погасила живую зону, потому что смотрела только на zone.pid. Теперь: процессы в cgroup vpn-zone@ не трогаются вовсе (ими управляет юнит); pasta убивается только если netns из её командной строки (/proc/N/ns/net) мёртв; чужие bwrap-песочницы не трогаются — в них работают программы. (`rust/src/cli.rs`, gc)

- **Второй эшелон (nftables) — страховка, и падать из-за него нельзя.** В обоих namespace зоны грузится таблица `inet vpnzone` с одной цепью `output` и `policy drop` (`docs/LEAK-MODEL.md`). Но `nf_tables` из непривилегированного userns НЕ автозагружается: если модуль не поднят на хосте, `nft` получит отказ ядра — и это не повод не поднимать зону, потому что герметичность держится топологией, а фильтр её только страхует. Поэтому любая неудача (`nft` нет, ядро отказало, ruleset не принят) — громкое `second echelon is OFF` в журнале держателя и продолжение работы. Смоук именно так и проверяет: либо правила стоят, либо предупреждение в журнале; «правил нет и все молчат» — красный тест. (`rust/src/zone.rs` `Zone::seal`/`feed_nft`, `tests/integration/smoke.sh`)

- **`oifname`, а не `oif`.** `oif` резолвится в ИНДЕКС интерфейса в момент загрузки правила: правило пришлось бы грузить после приезда awg0, а при пересоздании интерфейса оно молча перестало бы совпадать (то есть зона потеряла бы сеть без единого сообщения). `oifname` сравнивает имя каждый раз — ruleset можно грузить ДО появления туннеля, чем мы и пользуемся. (`rust/src/zone.rs` `app_ruleset`)

- **Адрес — это `ip daddr`/`ip6 daddr`, «udp daddr» не существует.** Правило аплинка — `ip daddr <сервер> udp dport <порт> accept`: адрес матчится на сетевом уровне, порт на транспортном. В таблице `inet` семейство подставляется само, и `nft list ruleset` печатает правило ровно в этом виде. (`rust/src/zone.rs` `uplink_ruleset`)

- **v6-endpoint без neighbour discovery не работает.** pasta даёт аплинку v6-default `via fe80::1`, и до первой отправки ядро обязано разрешить этот адрес — NS/NA, то есть ICMPv6, то есть output-хук `inet`. С `policy drop` без явного исключения туннель не отправит ни одного пакета. Поэтому при v6-endpoint в ruleset добавляется `icmpv6 type { nd-router-solicit, nd-neighbor-solicit, nd-neighbor-advert } accept`. Для v4 ничего подобного не нужно: ARP живёт в отдельном семействе `arp` и фильтром `inet` не ловится вообще. (`rust/src/zone.rs` `NDP_RULE`)

- **Роуминг endpoint'а обрежется фильтром.** WireGuard обновляет адрес пира, получив от него аутентичный пакет с другого адреса; правило аплинка выписано под адреса из конфига, и после такого переезда исходящие в новый адрес будут отброшены. Для статического сервера этого не случается, а «тихо разрешить всё» было бы отказом от смысла правила — но помнить об этом стоит, симптом выглядит как внезапно умерший туннель. (`rust/src/zone.rs` `uplink_ruleset`)

- **Прочитать ruleset изнутри зоны нельзя, и это фича.** nfnetlink требует CAP_NET_ADMIN даже на чтение, а программы входят в зону под обычным uid, где capabilities обнуляются на execve (§1) — снять или посмотреть правила они не могут. Следствие для тестов: смоук ходит за `nft list ruleset` через `nsenter` БЕЗ `--preserve-credentials`, чтобы оказаться внутри uid 0 (тот же приём, что и `setuid 0` у самого держателя). (`tests/integration/smoke.sh` `in_zone_root`)

## 2а. Бэкенд OpenConnect (userspace-клиент в аплинке)

- **`TUNSETIFF` спрашивает CAP_NET_ADMIN у ВЛАДЕЛЬЦА netns, а не у root хоста.** Именно поэтому `openconnect` создаёт tun внутри непривилегированного userns и root не нужен: netns аплинка принадлежит нашему же user namespace, а мы в нём uid 0 со всеми capabilities. От самого узла `/dev/net/tun` требуется только `crw-rw-rw-` (так его отдают все дистрибутивы) — проверять стоит именно права узла, а не «есть ли root». Тот же довод объясняет, почему приложение В ЗОНЕ так не сможет: оно входит туда обычным uid, capabilities обнуляются на execve (§1). (`rust/src/openconnect.rs`, шапка)

- **tun ПЕРЕЕЗЖАЕТ между netns из-под работающего клиента, и это не хак.** Устройство и дескриптор — разные вещи: дескриптор адресует ОЧЕРЕДЬ, устройство живёт в namespace. `ip link set <tun> netns <pid>` двигает устройство, очередь продолжает работать, и `openconnect` читает и пишет пакеты из аплинка, пока интерфейс, на котором они появляются, лежит в зоне приложений. Это зеркальное отражение свойства WireGuard (сокет остаётся там, где создан интерфейс) — и приём известный: так делает `vpnns` и его же рекомендуют рецепты «per-app VPN через netns». Именно на этом стоит весь бэкенд: TLS-сессия и адрес шлюза остаются этажом выше. (`rust/src/openconnect.rs`)

- **Устройство приезжает ВЫКЛЮЧЕННЫМ и без адресов.** `dev_change_net_namespace` гасит интерфейс и снимает с него адреса и маршруты. Поэтому app-ns обязан сам поднять его и настроить, и это не дублирование WireGuard-пути, а то же самое требование: netlink работает по ТЕКУЩЕМУ netns (§2). В зазоре между переездом и настройкой клиент уже пишет пакеты — они молча пропадают, что и есть правильное поведение.

- **`--script` запускается через `/bin/sh -c`, то есть строка разбирается шеллом.** `openconnect` не `execve`'ит скрипт напрямую. Store-путь шелл-символов не содержит, но держатель, запущенный руками из непривычного места, — может, поэтому путь проверяется. И `/bin/sh` обязан существовать в mount-namespace аплинка (он копия хостового, так что существует везде, где существует у хоста).

- **Ненулевой код скрипта на `connect` рвёт соединение — и это нужное поведение.** `openconnect` считает `connect` фатальным: не смогли переставить интерфейс за стену — соединения не будет вовсе. Fail-closed достаётся даром, ломать не надо.

- **`disconnect` не должен ничего разбирать.** Устройство исчезает вместе с дескриптором клиента и уносит с собой единственный маршрут app-ns. Скрипт только убирает файл плана. Соблазн «на всякий случай опустить интерфейс» вреден: он потребовал бы входить в чужой netns из скрипта, то есть ещё одного места, где что-то может пойти не так.

- **`reconnect` и `attempt-reconnect` — ничего.** Устройство и адрес те же, разбирать и настраивать нечего; штатный `vpnc-script` поступает так же. Пока идёт `attempt-reconnect`, зона мертва (пакеты пропадают) — это fail-closed, а не пауза. Открытый случай: шлюз, выдающий на реконнекте ДРУГОЙ адрес, оставит зону со старым и без связи (ROADMAP M4).

- **Клиент нельзя оставлять сиротой: `PR_SET_PDEATHSIG`.** Аплинк гасят обычным сигналом с дефолтной реакцией, никакой Drop и никакой обработчик на выходе не сработают — а осиротевший `openconnect` продолжил бы держать namespace аплинка с живой VPN-сессией внутри. Поэтому клиент стартует с `PR_SET_PDEATHSIG=SIGKILL`, а сам аплинк не паркуется на `pause()`, как в WireGuard-зоне, а ждёт клиента: смерть клиента = смерть аплинка = держатель гасит зону.

- **Имя интерфейса навязывается клиенту (`--interface awg0`).** Второй эшелон в app-ns грузится ЗАДОЛГО до приезда туннеля и называет `awg0` по имени (`oifname`, §2); интерфейс с любым другим именем молча ловил бы `policy drop` НАШЕГО ЖЕ фильтра. Приехало другое имя — зона не поднимается, с внятным текстом.

- **Правило аплинка для OpenConnect — без порта.** DTLS уходит на UDP-порт, который выбирает сервер, и номер неизвестен, пока сессии нет: правило `ip daddr <шлюз> accept` шире WireGuard'ского ровно на это измерение. «Только этот шлюз и ничего больше» сохраняется. (`rust/src/zone.rs` `Backend::sockets`)

- **Шлюз — тоже вход, и его данные надо проверять.** `INTERNAL_IP4_DNS` и `CISCO_DEF_DOMAIN` едут в resolv.conf зоны; если писать их как есть, шлюз может вписать туда СВОЮ строку (перевод строки плюс `nameserver …`) и подменить резолвер зоны, не имея к ней никакого доступа. Поэтому резолвер обязан парситься как адрес, домен — состоять из символов домена, а `TUNDEV` — быть именем интерфейса (он едет в командную строку `ip`). (`rust/src/openconnect.rs` `plan`)

- **`Args =` — белый список И форма.** Значение обязано быть записано `--флаг=значение`, а не двумя словами: иначе `Args = --useragent --script` протащил бы запрещённый флаг «значением», которое `openconnect` прочитает как флаг при первом же изменении порядка разбора. В список не входят `--script`, `--csd-wrapper`, `--external-browser`, `--setuid`, `--no-system-trust`, `--allow-insecure-crypto` — первый заменил бы единственное, что уводит туннель за стену, следующие два запускают программу по выбору СЕРВЕРА, остальные снимают проверку сертификата. Отдельно и сознательно не вошли три ФЛАГА СОВМЕСТИМОСТИ, каждый из которых ослабляет сам туннель: `--deflate` (сжатие до шифрования, класс VORACLE/CRIME — обратный `--no-deflate` разрешён), `--dtls-ciphers` (слабее криптография транспорта; шлюзу с экзотическими шифрами полагается `--no-dtls`) и `--passtos` (класс трафика изнутри туннеля переносится на внешние пакеты).

- **Окружение клиента собирается с нуля, а не наследуется.** `openconnect` уважает `https_proxy`/`http_proxy`/`HTTPS_PROXY`/`all_proxy`/`no_proxy` — переменная из сессии пользователя отправила бы клиента к прокси вместо шлюза. Второй эшелон такой пакет отбросит, но зона не должна спасаться страховкой от собственного старта. Переживают ровно четыре переменные, и каждая по названной причине: `PATH` (при запуске держателя руками скрипт и `ip` ищутся по нему), `HOME` (сетевого смысла нет, но без него библиотеки ломаются странно) и `SSL_CERT_FILE`/`NIX_SSL_CERT_FILE` — это ГДЕ ЛЕЖИТ системное хранилище CA: на NixOS gnutls пропатчен читать их, и очистить их значило бы оставить зону без пина неспособной проверить хоть что-нибудь. Заодно выбрасывается унаследованный `VPN_ZONE_OC_*`. (`rust/src/openconnect.rs` `client_env`/`CLIENT_ENV_KEPT`)

- **`sha1:`-пин не принимается, хотя `openconnect` его понимает.** Пин — это ВСЁ решение о доверии для зоны, у которой он есть; разрешить SHA-1 значило бы дать способ ослабить проверку сертификата через конфиг. Клиент сам печатает `pin-sha256:`, так что тянуться к слабому варианту незачем. (`rust/src/openconnect.rs` `is_fingerprint`)

- **Проверка владельца файла пароля обязана молчать под uid 0.** Тот же код исполняется дважды: в `cellward add` под пользователем (там чужой файл — повод отказать) и внутри userns зоны, где мы uid 0, а все uid в маппинге и так пользовательские. Сравнение `getuid()` там отвергло бы ЛЮБОЙ файл пароля. (`rust/src/openconnect.rs` `check_password_file`; §1 про двойной маппинг)

- **Имя шлюза резолвится заранее и отдаётся клиенту через `--resolve`.** Ровно та же грабля, что с `Endpoint` у WireGuard (§2), только по двум причинам сразу: в аплинке нет своего резолвера, а его фильтр не выпустил бы запрос наружу. Следствия: у шлюза с несколькими A-записями используется адрес, разрезолвленный на старте (смена адреса = перезапуск зоны), а имя, резолвящееся ТОЛЬКО в IPv6, отвергается — `--resolve` принимает `HOST:IP` и v6-адрес в этом формате однозначно не выражается.

- **Ловить отпечаток сертификата в тестах — у самого клиента.** `openconnect` при неудачной проверке печатает готовую строку `--servercert pin-sha256:…`; считать SHA-256 от DER своими руками значит однажды разойтись с ним в формате. Смоук так и делает: спрашивает клиент, потом кладёт ответ в конфиг зоны. (`tests/integration/smoke.sh`)

## 3. DNS

- **Резолверы хоста — unix-сокеты, и топология их не закрывает.** Имя резолвится обращением к демону по unix-сокету, а сокет — не интерфейс: у него нет маршрута, который можно убрать, нет интерфейса, через который он «выходит», и нет пакета, который увидел бы фильтр. Демон на том конце сидит в сети хоста и отвечает оттуда. Поэтому герметичность namespace тут не помогает вообще, и подмена resolv.conf — тоже. Обе утечки измерены на живой зоне:
  - **nsncd** (`/run/nscd/socket`, в NixOS работает по умолчанию): `getent` отвечал при RX=0 на awg0 — запрос ни разу не коснулся туннеля;
  - **systemd-resolved** (`/run/systemd/resolve/io.systemd.Resolve`, varlink): в NixOS с включённым resolved модуль `resolve` стоит в `/etc/nsswitch.conf` ПЕРЕД `dns`, поэтому через него шёл КАЖДЫЙ запрос из зоны. Симптом: leak-тест в браузере внутри зоны называет реального провайдера пользователя как резолвер, а `curl ifconfig.me` в той же зоне честно показывает адрес VPS. Верный признак — `resolvectl status`, запущенный внутри зоны, вообще отвечает: значит, сокет хостового resolved в зоне виден.
  Лечение одно на всех: пустой tmpfs поверх каталога с сокетом внутри зоны (`/run/nscd` или `/var/run/nscd`, `/run/systemd/resolve`, `/run/avahi-daemon` — nss-mdns вынес бы имя в LAN хоста). Дерево монтирования у зоны private, так что остальной системе демоны служат как прежде; glibc внутри зоны сокета не находит, nss-resolve отвечает UNAVAIL — ровно тот случай, который `[!UNAVAIL=return]` в nsswitch пропускает дальше, — и модуль `dns` идёт к серверам из resolv.conf зоны, то есть в туннель. Неудача сокрытия — фатальна для зоны (fail-closed): зона, чьи программы резолвят имена в сети хоста, хуже отсутствующей, потому что выглядит рабочей. Сокрытие делается ДО ветки offline-зоны: «оффлайн» с видимым сокетом резолвера — это канал наружу, в имя хоста можно закодировать данные. (`rust/src/zone.rs`, `hide_host_resolvers`/`RESOLVER_DIRS`; регрессия — `tests/vm.nix`, подтест «no DNS leak»)

- **Остаточный канал: resolve1 по системной шине D-Bus.** Сокет `/run/dbus/system_bus_socket` в зоне остаётся видимым, а через него доступен `org.freedesktop.resolve1` хоста — именно поэтому `resolvectl` внутри зоны отвечает даже после сокрытия varlink-сокета. Через getaddrinfo этот путь не используется (glibc ходит только в NSS), в fs-sandbox системной шины нет вовсе, так что для программ канал закрыт; но программа, которая ЗАХОЧЕТ резолвить через D-Bus, всё ещё сможет. Закрывать его сокрытием всей системной шины — заметная потеря функциональности (UPower, NetworkManager, logind), поэтому решение отложено и записано в ROADMAP.

- **Свой nsswitch.conf зоны закрывает класс, а не список.** Сокрытие сокетов резолверов — перечисление (nscd, systemd-resolved, avahi), и следующий NSS-модуль, говорящий с демоном хоста, в него не попадёт: `mymachines` уже спрашивает machined по системной шине. Зона биндит свою копию `/etc/nsswitch.conf` хоста, где `hosts:` сведено к `files dns`: для имени не грузится ничего, кроме обычного резолвера, а он читает resolv.conf зоны. Остальные базы (`passwd`, `group`) не трогаются — это не сетевой канал. Бинд — поверх конца цепочки симлинков, как у resolv.conf; отказ — громкое предупреждение, а не падение зоны: сокеты и так спрятаны, теряется страховка класса. (`rust/src/zone.rs` `own_nsswitch`, `zone_nsswitch`)

- **Системная шина в зоне — через свой прокси, а без прокси — никак.** resolve1 — тот же резолвер хоста, только по D-Bus, а NetworkManager отвечает любой программе, в каких сетях на самом деле машина: деанон без единого пакета. Юнит зоны поднимает `xdg-dbus-proxy` к системной шине ДО зоны (сокет в каталоге зоны), зона одним из первых шагов биндит его сокет поверх `/run/dbus/system_bus_socket`. Разрешено только UPower и у login1 — `Inhibit` и чтение свойств (решение владельца B2). Прокси не поднялся — в зоне tmpfs поверх `/run/dbus`: шины нет вовсе, но и хостовой нет; не удалось и это — зона не поднимается. Прокси запускается от uid пользователя, а не от держателя: uid 0 внутри user namespace зоны — это subuid на хосте, и системная шина видела чужака, а программа в зоне предъявляла uid пользователя — аутентификация не сходилась, и через такой прокси не проходил ни один вызов, разрешённые тоже (отказы при этом выглядели как работа фильтра — поэтому VM-тест проверяет и разрешённое чтение). И запускает его сам процесс юнита, в пространстве пользователя ХОСТА, а не держатель: в пространстве зоны, с uid её программ и dumpable после `exec`, прокси читался бы программой зоны через `/proc/<pid>/root` — файловая система хоста без покрытий зоны, шина без фильтра (LEAK-MODEL §16, `zone::Helpers`; так же фильтр звука и прокси сессионной шины герметичной зоны). Смерть прокси зону не роняет: бинд на мёртвый сокет — отказ в соединении, то есть закрыто. `doctor` отличает «фильтруется» и «закрыта» по `/proc/self/mountinfo`. (`rust/src/zone.rs` `start_system_bus_proxy`, `seal_system_bus`, `SYSTEM_BUS_RULES`; VM-тест — подтест «system bus in a zone»)

- **X11 в зоне: tmpfs поверх `/tmp/.X11-unix`, и не только ради хоста.** `/tmp` у зон общий с хостом и между собой: X-сервер, поднятый в одной зоне без tmpfs, положил бы сокет туда, где его видят все зоны, — и программа одной личности читала бы окна и ввод другой. Поэтому tmpfs создаётся всегда (каталог создаётся, если на хосте его нет), а `DISPLAY`/`XAUTHORITY` убираются из запуска в зону: иначе тулкиты сначала пробуют X, падают и не доходят до Wayland. Контейнеру с `x11` свой `xwayland-satellite` запускает `x11-run` — ВНУТРИ `wl-sandbox` (обёртка вокруг обёртки), чтобы спутник говорил с композитором через ограниченный сокет; спутник умирает вместе с обёрткой (`PR_SET_PDEATHSIG`), а номер дисплея берётся первый свободный в tmpfs зоны. Абстрактные X-сокеты хоста зоне не видны и так: они живут в сетевом namespace. (`rust/src/zone.rs` `hide_x11`, `rust/src/x11.rs`, `rust/src/launch.rs`)

- **Герметичная зона: свой runtime-каталог строится поверх хостового, а хостовый тут же отпускается.** tmpfs поверх `/run/user/<uid>` закрывает всё сразу — и то, что нужно вернуть (сокет композитора, PipeWire, Pulse, `doc` портала). Поэтому сначала хостовый каталог биндится во временную точку в каталоге зоны, потом tmpfs (владелец — пользователь), потом из временной точки назад биндится только разрешённое, отфильтрованная шина — как `bus`, сокет брокера — как `vpn-zones/broker`, и временная точка отцепляется (`MNT_DETACH`): каталог зоны программам виден, и через него хостовый runtime остался бы доступен целиком. `systemd/private` и хостовый `bus` не возвращаются — это и есть два способа запустить процесс вне зоны. Делегирование запуска из зоны выбирает брокера по отсутствию `systemd/private`, а не по переменной окружения, которую программа могла бы выставить; брокер узнаёт зону по сетевому namespace собеседника, а не по запросу. Собеседник закрепляется в момент соединения — pidfd того самого процесса от ядра (`SO_PEERPIDFD`, Linux 6.5; раньше — открытый по pid сразу), namespace читается, только пока этот процесс жив (до и после чтения), и всё, что не хост и не зона, — отказ. Раньше «не зона» значило «хост» и запускалось без вопроса: программа герметичной зоны, успевшая выйти до того, как брокер посмотрел в `/proc`, получала свою команду на хосте, в сети хоста (найдено аудитом 2026-09-24). (`rust/src/zone.rs` `seal_runtime`, `rust/src/broker.rs` `origin_of`; VM-тест — подтест «hermetic zone», тест `a_peer_that_left_before_it_was_looked_at_is_unknown`)

- **resolv.conf зоны — mount --bind, видимый только внутри.** DNS из конфига пишется в файл зоны и бинд-монтируется поверх /etc/resolv.conf; без этого запросы уходили бы к резолверу хоста мимо туннеля — самая частая утечка. У остальной системы /etc/resolv.conf прежний. (`rust/src/zone.rs`, `resolv_conf`)

- **Бинд поверх /etc/resolv.conf садится НЕ на /etc/resolv.conf.** `mount(2)` разыменовывает симлинки в цели, а в NixOS это цепочка: /etc/resolv.conf → /etc/static/resolv.conf → /run/systemd/resolve/stub-resolv.conf. То есть монтируется поверх файла В ТОМ САМОМ каталоге, который зона только что закрыла tmpfs-ом, и последний симлинк повисает: mount падает с голым ENOENT, а зона — вместе с ним. Поэтому цепочка проходится руками (`sys::link_target`; `fs::canonicalize` не годится — он требует существования всех компонентов), недостающий файл создаётся в tmpfs, и уже поверх него идёт бинд. Побочный выигрыш: в каталоге не остаётся ни `resolv.conf` хоста с его настоящими серверами, ни сокета. (`rust/src/zone.rs`, `sys::link_target`)

- **В песочницу пробрасывается ФАЙЛ resolv.conf, а не его каталог.** /etc/resolv.conf — цепочка симлинков, кончающаяся вне /etc (в NixOS — в /run/systemd/resolve), а сам /run в bwrap не пробрасывается: без этого файла имена в песочнице не резолвятся вовсе. Но каталог пробрасывать нельзя — рядом с файлом лежит varlink-сокет хостового resolved, и nss-resolve резолвил бы через него в сети хоста, мимо туннеля (та самая измеренная утечка выше). Внутри зоны цепочка приводит к resolv.conf самой зоны, а сокета там уже нет; если файла нет вообще — не пробрасывается ничего, и песочница теряет имена, а не зона герметичность. (`rust/src/fs_sandbox.rs`, `bwrap_args`/`resolv_file`)

## 4. Конфиги WireGuard/AmneziaWG

- **Мёртвый туннель — не «старое рукопожатие», а «шлёт в тишину».** WireGuard рукопожимается только когда есть что отправить: у простаивающего туннеля рукопожатие старое, и он исправен. Мёртвый — тот, у которого счётчик отправленного вырос с прошлого взгляда, полученного — нет, а последнее рукопожатие старше 180 с (`REJECT_AFTER_TIME`) или его не было вовсе. Один взгляд может попасть между пакетом и ответом, поэтому смерть объявляется, когда два взгляда подряд согласны; тихий взгляд (ничего не отправлено) сохраняет последнее известное состояние; счётчики, которые уменьшились, — перезапуск зоны, сравнивать нечего. Уведомление — одно при смерти и одно при возвращении, память между запусками — `.watch/<зона>`. Утечки мёртвый туннель не даёт: выход просто закрыт, и об этом надо сказать человеку. (`rust/src/watch.rs`)

- **awg setconf понимает только ключи протокола.** Address/DNS/MTU/Table/PreUp/PostUp/PreDown/PostDown/SaveConfig — указания wg-quick: их надо вычистить из файла (иначе setconf падает на первой же такой строке) и применить руками: адреса — ВСЕ из списка через запятую, обоих семейств, MTU по умолчанию 1420. (`rust/src/config.rs` `to_setconf` + `rust/src/zone.rs`)

- **CRLF от Amnezia.** Amnezia отдаёт .conf в формате Windows — проверено на настоящем файле: 21 строка с \r. «\r» попадает в конец значения, и зона падает на первой команде: `ip addr add 10.8.1.10/32<CR>` → «inet prefix is expected rather than "10.8.1.10/32"» — ошибка выглядит бессмысленно, потому что возврат каретки в сообщении не виден. Чистить надо и при `cellward add`, и повторно при подъёме зоны: конфиг могли положить в каталог зоны руками. (`rust/src/cli.rs` add + `rust/src/config.rs`)

- **Пустые параметры I1…I5 валят setconf целиком.** Свежая Amnezia кладёт параметры пакетов-приманок I1…I5 и заполняет не все: получается «I2 = ». awg setconf на такой строке падает целиком — «Line unrecognized: `I2='» — и зона не поднимается вовсе (проверено на двух реальных конфигах: старый набор Jc/S/H работал, новый с I1…I5 — падал). Выбрасывать только строки с пустым значением: заполненные параметры обфускации обязательны, без них сервер не ответит. (`rust/src/config.rs`)

- **Конфиг — копия mode 600, не симлинк.** Файл с приватным ключом должен пережить перемещение и удаление исходника (`install -m 600 /dev/null`, затем запись). При удалении зоны копия стирается — восстановить ключ неоткуда, поэтому GUI удаления обязан переспрашивать вторым шагом. (`rust/src/cli.rs` add; `rust/src/gui.rs` remove)

- **Первое рукопожатие — главный признак «конфиг живой».** Зона через ~4 с печатает в журнал, прошло ли рукопожатие (`awg show awg0 latest-handshakes`); GUI-добавление ждёт 6 с и сразу сообщает, живой ли конфиг — ради этого ответа зону обычно и создают («какой из моих .conf ещё работает?»). (`rust/src/zone.rs` `handshake_seen`; `rust/src/cli.rs` check; `rust/src/gui.rs` add)

- **`awg show` изнутри под обычным uid молчит; «нет данных» ≠ «нет рукопожатия».** awg show требует прав на netlink, а программы и `cellward status` заходят в зону под обычным uid — состояние туннеля было недоступно вообще. Поэтому зона сама изнутри (где права есть) пишет зеркало состояния в файл каждые 5 с, атомарно через mv. `cellward check` при отсутствии файла зеркала (зона поднята старой версией) не объявляет живой туннель мёртвым, а просит перезапустить зону — отдельный код выхода. (`rust/src/zone.rs` `start_status_mirror`; `rust/src/cli.rs` status/check)

## 5. Overlayfs, профили, контейнеры

- **Хранилище профилей в `.local/state` — не вкусовщина.** Верхний слой overlayfs не может находиться на overlayfs. Пока хранилище лежало в .local/share, первые два каталога монтировались, а на .cache и дальше ядро отвечало EINVAL: их upperdir оказывался уже накрыт предыдущим слоем. .local/state в список накрываемых каталогов не входит — конфликта нет. (`module/default.nix`, profilesDir)

- **Профиль монтируется при запуске программы, а не при подъёме зоны.** Первым заходом слой данных накладывался прямо в zoneInit, на всю зону — и профиль оказывался намертво привязан к VPN: заблокировали сервер — настроенное окружение «уехало» вместе с ним. Теперь профиль — отдельная сущность вне каталога зон: тот же профиль можно поднять в другой зоне или вовсе без VPN. (`rust/src/zone.rs` + `rust/src/profile.rs`)

- **Слой накрывает только XDG-каталоги; документы общие намеренно.** Overlay (с опцией userxattr) — на .config, .local/share, .cache, .mozilla, .pki. Downloads/Documents и прочее содержимое $HOME общие: это разделение профилей, а не песочница. Профиль «основной» — пустая строка: слои не накладываются вовсе. (`rust/src/profile.rs`)

- **Одноразовый контейнер: fork+wait вместо exec, удаление только за последним жильцом.** exec нельзя — кто-то должен пережить программу и убрать каталог. Точки монтирования чистить не надо: mount namespace умирает с последним процессом. Слой стирается только когда по общему реестру запусков не осталось живых (в контейнер можно подсадить несколько программ через `--tmp-profile --join`; удаление по выходу первой отняло бы ФС у остальных). Оговорка: программа, отправляющая себя в фон с завершением первого процесса, лишится каталога из-под ног (браузеры и Electron так не делают). Брошенные при жёстком убийстве каталоги `vpn-profile-*` подчищает gc. Каталоги живут на диске сознательно, чтобы кэш браузера не съел оперативку, — в `~/.local/state/vpn-zones/.throwaway/`; раньше жили в `/tmp`, но у герметичной зоны `/tmp` свой, и слой, созданный на хосте, в ней не нашёлся бы (LEAK-MODEL §15). gc и пикер смотрят и в старое место — для контейнеров, запущенных до переезда. (`rust/src/profile.rs`, `rust/src/launch.rs`, `rust/src/cli.rs` gc)

- **«Думал, что под VPN»: у браузеров один процесс на профиль.** Второй запуск находит сокет первого, отдаёт ему «открой окно» и выходит: окно ОТКРЫВАЕТСЯ и выглядит совершенно нормально, но рисует его старый процесс в старой сети. Отличить такое поведение заранее нельзя — это свойство программы (alacritty, например, ведёт себя иначе), списком не покрыть — поэтому ПРЕДУПРЕЖДЕНИЕ с галочкой «не спрашивать снова» (kdialog --dontagain), а не запрет; проверка конфликтов — в пределах одного профиля (основной — ключ `__main__`). Из терминала без графики диалог показать негде: предупреждаем в stderr и продолжаем — молча отменять запуск хуже. По той же причине `isolate off` явно предупреждает, что браузер откроет окно в уже запущенном процессе мимо VPN. (`rust/src/launch.rs` + `rust/src/cli.rs` isolate)

- **Ключ «уже запущена в другой сети» — и app-id, и бинарь.** Ключ реестра — `VPN_ZONE_APPID`, если он есть, иначе первое слово команды, и две `.desktop`-записи на один однопроцессный бинарь друг друга не видели: игра Steam (`--id PEAK`, `Exec=steam steam://rungameid/…`) и сам Steam, firefox и firefox-private, веб-приложения на chromium, варианты Telegram. Вторая отдавала работу уже запущенному процессу — в ЕГО сети — и предупреждение молчало. Теперь каждая запись дублируется в индексе по бинарю (`.running/<контейнер>/.by-binary/<бинарь>`), и предупреждение смотрит в оба. Индекс отвечает ТОЛЬКО на «запущена ли где-то ещё»: куда направить клик по уже запущенной программе, по-прежнему решает id — многооконную программу (терминал) нельзя затащить в чужую сеть по совпадению имени бинаря. Каталог точечный, поэтому ни один из четырёх читателей реестра не примет его за программу; `gc` подчищает и его. Текст предупреждения для ССЫЛКИ (аргумент с `://`) свой: «окно откроется» для неё неверная картина — ссылку (и игру с ярлыка Steam) примет процесс, уже живущий в другой сети. (`rust/src/launch.rs` `hands_over_a_link`, `rust/src/registry.rs` `BY_BINARY`)

- **Блокировка реестра — flock на открытый дескриптор `.lock`, снимается закрытием.** В bash это был `( … ) 9>>"$regdir/.lock"`: замок жил, пока жив сабшелл. В Rust — `libc::flock(LOCK_EX)` на том же файле, а снимает его Drop (закрытие дескриптора), поэтому критическая секция — это область видимости переменной-стража, и её нельзя случайно «продлить». Файл замка тот же самый, так что старый bash-`vpn-zone` и новый бинарь во время переключения поколений home-manager по-прежнему исключают друг друга. Имя начинается с точки не для красоты: shell-глобы `*/*` точечные имена не видят, и обход реестра в крейте обязан пропускать их так же — иначе gc принял бы замок за файл записей и «подчистил» бы его. (`rust/src/registry.rs`)

- **Реестр запусков: $$ переживает exec, третье поле — селектор.** PID не меняется при exec, поэтому запись «pid зона селектор» остаётся верной всё время работы; мёртвые записи чистятся лениво при следующем запуске. Третье поле фиксирует, ЧТО было выбрано (песочница/разовая песочница/профиль): без него повторный клик по ярлыку уже запущенной программы возвращал её «голой» — сеть из реестра бралась, а песочница терялась, потому что при песочнице profile пуст и ключ каталога всегда получался `__main__`. (`rust/src/launch.rs`)
- **PID — не процесс: время старта рядом с записью реестра и с `zone.pid`.** Реестр лежит на диске и переживает перезагрузку, а записи чистятся лениво — следующим запуском той же программы. После перезагрузки каждое число в нём скоро принадлежит кому-то другому (в длинной сессии числа тоже идут по кругу), и «жив ли процесс с этим pid» отвечало «да» за чужой процесс. Пикер тогда считал программу запущенной и отправлял клик в её прошлую сеть без вопроса — `unconfined` тоже. Теперь `cellward run` пишет рядом с записью время старта процесса (`.running/.started/<pid>`, поле 22 `/proc/<pid>/stat`: число повторяется, число вместе со временем старта — нет). Четвёртым полем не стало: форма записи — контракт (селектор забирает остаток строки), и старый бинарь во время переключения поколений должен её читать. Две проверки: `registry::launched` (время записано и совпадает) — для того, что запись делает БЕЗ вопроса: «уже запущена — туда же» у пикера, зона окна у `cellward focused`; `registry::alive` (запись со временем — по времени, старая без него — по pid, как раньше) — там, где безопасно считать программу работающей: отказ открыть контейнер во второй сети, сохранение разового контейнера, уборка. Так же `zone.pid`: держатель пишет рядом `zone.start`, и остановленная зона, чьё число досталось другому процессу, не «поднята». Иначе `cellward run` вошёл бы в namespace чужого процесса, и если тот в сети хоста — в своём user namespace, как у разового контейнера `unconfined` или Flatpak, — программа ушла бы в сеть хоста под именем зоны. На этот случай есть и последняя проверка прямо перед `exec`: процесс зоны в НАШЕМ сетевом namespace — не зона, запуск останавливается. (`rust/src/registry.rs` `STARTED`, `rust/src/cli.rs` `zone_pid`, `rust/src/zone.rs` `START`, `rust/src/launch.rs` `in_our_network`; тесты `a_record_whose_number_went_to_another_process_does_not_skip_the_question`, `a_zone_whose_process_is_in_our_network_is_not_entered`)

## 6. bwrap-песочница и порталы

- **`/.flatpak-info` — переключатель на порталы.** Приложение идёт через порталы, только если считает себя изолированным, а проверяет это по наличию /.flatpak-info (так делают GTK, Qt, Chromium, Electron). Хватает минимальной секции [Application]; файл монтируется только на чтение. С ним файловый диалог рисует чужой процесс и отдаёт ровно один выбранный файл (document-portal), камера и запись экрана начинают спрашивать разрешение — «андроидные» запросы получаются даром. (`rust/src/fs_sandbox.rs`)

- **Разрешения: раз на программу; у именованной песочницы — на песочницу; без графики — «ничего».** Разрешения именованной песочницы общие для всех её программ — иначе вторая спрашивала бы заново про тот же самый дом. Без WAYLAND_DISPLAY/DISPLAY диалог показать негде и ждать ответа некому — программа просто зависла бы (проверено); в этом случае молча пишется пустой набор разрешений. (`rust/src/fs_sandbox.rs`)

- **Идентификатор разрешений — id ярлыка, не имя бинаря.** Иначе разрешения двоятся: у Discord ярлык даёт «discord», а бинарь называется «Discord» — получались два независимых набора доступов на одну программу. Берётся VPN_ZONE_APPID (ключ пикера), имя бинаря — только при его отсутствии. (`rust/src/launch.rs`)

- **mimeapps.list пробрасывать на чтение.** В песочнице ~/.config пуст, mimeapps.list не виден, и xdg-open подбирает обработчик сам: у Discord ссылка на вход открывалась в Chrome, хотя браузер по умолчанию — zen. Файл крошечный и без секретов — пробрасывается только он и только read-only. (`rust/src/fs_sandbox.rs`)

- **NVIDIA: одного /dev/dri мало.** Драйверу нужны ещё узлы /dev/nvidia*: без них EGL внутри падает («failed to create dri2 screen»), а Electron намертво виснет на заставке — проверено на Discord. (`rust/src/fs_sandbox.rs`)

- **seccomp: вложенные user namespace запрещать НЕЛЬЗЯ.** У flatpak в базовом наборе такой запрет есть, но там же есть zypak, переводящий песочницу Chromium на порталы. В NixOS нет ни zypak, ни setuid chrome-sandbox, поэтому Chromium и все Electron-программы строят СВОЙ вложенный userns: запретишь `clone`/`unshare` с `CLONE_NEWUSER` — и они не стартуют вовсе («No usable sandbox! Update your kernel»). Наружу такой userns не выводит: права он даёт только над своими новыми пустыми namespace. Запрет остаётся отдельным флагом (`vpn-zone-seccomp export --deny-userns`) для программ, которые сами себя не изолируют. (`rust/src/seccomp.rs`, `rust/src/fs_sandbox.rs`)

- **Фильтр передаётся ДЕСКРИПТОРОМ, и с Rust это делается в pre_exec.** `bwrap --seccomp` принимает только номер fd (не путь). В bash файл открывался заранее (`exec 34< …`), потому что редирект нельзя положить в массив аргументов. Теперь фильтр собирается в самом процессе (`crate::seccomp::Filter::export_to_file`), а нужный номер получается `dup2(fd, 34)` в `Command::pre_exec` — dup2 заодно снимает `FD_CLOEXEC`, ради чего он и выбран. Отдельная ветка на случай, когда исходный fd уже равен 34: тогда dup2 — no-op и CLOEXEC не снимет, надо `fcntl(F_SETFD, 0)` руками. И ещё: bwrap читает с ТЕКУЩЕЙ позиции, поэтому файл обязан быть перемотан в начало. Не собрался фильтр — предупреждение в stderr и запуск без него: мягкая деградация, как в остальных слоях. (`rust/src/fs_sandbox.rs`, `rust/src/seccomp.rs`)

- **bwrap запускать НЕ через exec; вывод dbus-прокси — в /dev/null.** После exec обработчик выхода (trap) уже не сработает, и xdg-dbus-proxy остался бы висеть. А открытый stdout прокси делает вызов «зависшим», хотя программа давно закончила. (`rust/src/fs_sandbox.rs`)

- **Прокси надо гасить и по СИГНАЛУ, не только по выходу программы.** В bash `trap` жил в сабшелле, и TERM, прилетевший этому сабшеллу, убивал его отдельно — xdg-dbus-proxy оставался висеть. Теперь TERM/INT перехватываются, передаются песочнице и прокси, а уборка (TERM, потом KILL для упрямого, и снос временного каталога) идёт общим Drop-путём, тем же, что и при обычном выходе. `--die-with-parent` закрывает только bwrap: прокси — наш процесс, не его. (`rust/src/fs_sandbox.rs`, `Cleanup`/`forward_stop`)

- **Не поднявшийся dbus-прокси не должен ронять запуск.** Сокет прокси биндился в bash БЕЗУСЛОВНО, и когда прокси не стартовал (нет сессионной шины, tty-логин, CI), bwrap падал на «Can't find source path» — программа не открывалась вовсе. Задумана была мягкая деградация: нет шины — плохо, нет программы — баг. Теперь бинда просто нет, а `DBUS_SESSION_BUS_ADDRESS` продолжает указывать внутрь runtime-tmpfs, где пусто: найти НАСТОЯЩУЮ шину программа не должна ни при каком исходе. Заодно ожидание сокета обрывается, как только прокси умер (pidfd), а срока у него нет вовсе: на загруженной машине прокси поднимается позже, а не «не поднимается» (2026-09-26; было пять секунд). (`rust/src/fs_sandbox.rs`, `start_bus_proxy`, `sys::wait_for_entry`)

- **`/run/current-system` биндить через `-try`.** Путь есть только на NixOS, а отсутствующий источник для `--ro-bind` — фатальная ошибка bwrap. С `-try` песочница работает и там, где nix есть, а NixOS нет (CI-раннер, nix-on-Debian) — на самой NixOS разницы никакой. (`rust/src/fs_sandbox.rs`, `bwrap_args`)

- **Порядок аргументов bwrap — это и есть песочница.** Операции применяются по порядку: tmpfs поверх `$HOME` обязан идти ДО точечных биндов Downloads/Documents/Pictures, а tmpfs поверх `XDG_RUNTIME_DIR` — до сокетов. Переставь — и разрешение молча перестанет работать или, наоборот, тихо откроется весь дом. По запущенной программе этого не видно, поэтому список собирается ЧИСТОЙ функцией и сравнивается в юнит-тестах поэлементно. (`rust/src/fs_sandbox.rs`, `bwrap_args`)

- **machine-id песочницы — сразу после `/etc`, и только поверх обычного файла.** `/etc` биндится целиком, и `/etc/machine-id` хоста — один идентификатор на все зоны и песочницы: две личности, которые не должны встречаться, делили его. Свой файл биндится СРАЗУ после `/etc` (раньше — `/etc` накрыл бы его). У именованной песочницы он лежит в её каталоге и постоянен — программа, регистрирующая «устройство», регистрирует его один раз; у одноразовой — новый на запуск, как и её дом. Если на хосте `/etc/machine-id` — symlink, ничего не биндится: bwrap пошёл бы по ссылке за пределы дерева песочницы. (`rust/src/fs_sandbox.rs` `sandbox_machine_id`)

- **Права каталогов — `--bind-try` и сообщение, а не `--bind`.** С `--bind`, как было в bash-версии, разрешение на несуществующий `~/Pictures` валило bwrap: программа не запускалась вовсе из-за галочки, которая ничего не даёт. Теперь каталог пропускается, а запуск говорит, какого нет. В настоящем доме ничего не создаётся — это было бы действием от имени программы. Выданные пути (`container grant`) остаются `--bind`: их каталог создаётся заранее, после проверки. (`rust/src/fs_sandbox.rs`, `bwrap_args`, `run`)

- **Формат файла разрешений — подстроки, а не токены.** bash проверял `case "$perms" in *home*)`, то есть искал подстроку во всём тексте файла. Именно поэтому продолжают работать старые файлы, записанные до `--separate-output`: там токены через пробел и в кавычках. Разбор в Rust делает ровно то же самое, и это безопасно ровно пока ни один токен не является подстрокой другого — на что есть отдельный тест. (`rust/src/fs_sandbox.rs`, `Perms::parse`)

- **XDG_RUNTIME_DIR — tmpfs, сокеты поимённо.** Пробрасываются только wayland-сокет (ограниченный: `wl-sandbox` обёрнут вокруг всего запуска и делает его на хосте ДО bwrap — пока он стоял внутри, песочнице пробрасывался сырой сокет композитора, LEAK-MODEL §13), pipewire/pulse и прокси шины; всё остальное из runtime-каталога программе не видно. DBUS_SYSTEM_BUS_ADDRESS снимается, FLATPAK_ID выставляется. (`rust/src/fs_sandbox.rs`)

- **Песочница ФС — только по явному флагу.** Включать её всем подряд нельзя: программа теряет доступ к привычным каталогам, и что именно ей нужно, выясняется поштучно. (`rust/src/launch.rs`)

- **Привязку ушедшего устройства не закрыть монтированием поверх — её надо сначала снять.** Песочница получает узел устройства привязкой, а привязка держит inode и после `rm` узла из `/dev` — откроет то устройство, что займёт номер следующим. Корень такой привязки — dentry удалённого узла, а монтировать на удалённый dentry ядро отказывается (`ENOENT`, `cant_mount`/`d_set_mounted`): `/dev/null` поверх не ляжет. Держатель зоны снимает привязку (`umount2(MNT_DETACH)`) и кладёт `/dev/null` на заглушку bwrap под ней. Для запусков это не нужно: их привязка стоит на заглушке в `/dev` зоны, и зона, удалив заглушку, снимает её во всех пространствах. (`rust/src/device_guard.rs` `revoke_everywhere`, VM-тест «sb-after»)

- **Точку монтирования с заблокированными детьми не скопировать без них.** `/dev` зоны пришёл из пространства хоста с `pts`, `shm`, `mqueue` поверх — они заблокированы (`MNT_LOCKED`), и `open_tree(OPEN_TREE_CLONE)` или `mount --bind` без рекурсии отказывают (`EINVAL`): копия обнажила бы то, что дети закрывают. Devtmpfs для своего `/dev` зона берёт рекурсивно (`AT_RECURSIVE`) и прячет вместе с детьми в каталоге `0700`. (`rust/src/sys.rs` `clone_tree`, `rust/src/zone.rs` `own_dev`)

- **fsuid с 0 обратно — и файловых capabilities больше нет.** `profile-run` делает заглушки в `/dev` зоны с `setfsuid(0)`, чтобы они сразу были root-а зоны. Вернуть fsuid пользователя — и ядро само вычищает из действующего набора `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, `CAP_DAC_READ_SEARCH`, `CAP_FOWNER` и соседей (capabilities(7)): слой дома после этого не монтировался (`EACCES`). После возврата действующий набор снова делается равным разрешённому. (`rust/src/profile.rs` `AsZoneRoot`)

- **Удалить заглушку — значит снять все привязки на ней.** Удаление файла, на который смонтировано что-то в *другом* пространстве имён, ядро не запрещает, а снимает эти монтирования, во всех пространствах, и в сделанных программами (в своём — `EBUSY`). Поэтому выданное запуску устройство привязано на заглушку в `/dev` зоны, а не на её собственную запись: устройство ушло — зона удаляет заглушку, и привязок нет нигде. (`rust/src/zone.rs` `DeviceWatch::gone`)

- **Снятая привязка не отнимает устройство у того, кто держит его inode.** Дескриптор на узел — даже `O_PATH`, который ничего не открывает, — переоткрывается через `/proc/self/fd/N` и откроет то устройство, что получило номер: права проверяются по старому inode (ACL сеанса на нём был), а открывается драйвер по номеру. Отнять дескриптор у чужого процесса нельзя, поменять права на inode devtmpfs держатель в своём пространстве пользователей не может — остаётся убить держащего, и не раньше, чем номер займёт другое устройство: геймпад, вернувшийся на свой номер, игру не роняет. Узнают «то же» по sysfs, а не по базе udev: узел появляется раньше, чем udev его разберёт. (`rust/src/device_guard.rs` `Worker::appeared`, `identity`)

## 7. Wayland и security-context

- **Механизм — помеченный сокет, а не «отказ».** Протоколы слежки (wlr-screencopy, data-control, virtual-keyboard/pointer, foreign-toplevel) выдаются любому клиенту без вопросов — в Wayland нет понятия «доверенный клиент». wp_security_context_v1: клиент создаёт ОТДЕЛЬНЫЙ unix-сокет, помечает его песочницей и отдаёт композитору; все подключившиеся через него считаются ограниченными. niri (функция client_is_unrestricted в его исходниках) и KWin такие протоколы им не выдают вовсе — программа не получает отказ, она их просто не видит (проверено: 47 протоколов против 33). Остаются: свои окна, ввод в них, буфер по Ctrl+C/Ctrl+V при фокусе, GPU, звук. (`rust/src/wl_sandbox.rs`, `rust/src/launch.rs`)

- **Нет протокола — запуск без ограничений, но с предупреждением.** Старый композитор или X11-сессия: молча ослаблять защиту нехорошо, поэтому предупреждение в stderr и обычный запуск (общий путь `run_plain` для всех случаев «не получилось»: нет XDG_RUNTIME_DIR, нет связи с композитором, нет протокола, не создался сокет или труба, композитор отверг контекст, не получился fork). Каждый такой путь закрыт интеграционным тестом `rust/tests/wl_sandbox_cli.rs`: потерять ограничение допустимо, потерять программу — нет. (`rust/src/wl_sandbox.rs`)

- **Механика сокета: close_fd-«выключатель», имя по pid, WAYLAND_SOCKET снять.** Композитор принимает соединения на помеченный сокет, пока открыт переданный ему конец трубы — держать его всё время работы программы и отпустить после выхода. Имя сокета уникально по pid: два запуска одной программы не должны драться за один путь. И обязательно снять `WAYLAND_SOCKET`: унаследованный дескриптор перебил бы WAYLAND_DISPLAY, и программа ушла бы на обычный сокет мимо всей затеи. По той же причине соединение с композитором закрывается ДО fork: неограниченный сокет, унаследованный программой, нашёлся бы через `/proc/self/fd`. (`rust/src/wl_sandbox.rs`)

- **Не exec, а fork+wait — и форма вызова с `--`.** После выхода программы надо закрыть «выключатель» и удалить сокет, поэтому ограниченный запуск идёт дочерним процессом (fallback-путь, наоборот, именно `execvp`: там убирать нечего). Вызов теперь `vpn-zone-core wl-sandbox <app-id> -- <кмд…>`: у прежней программы на C разделителя не было, и лишний позиционный аргумент молча становился программой. Код выхода — программы; убитая сигналом даёт `128 + N`, как в `profile-run` (в C-версии был плоский `1`). (`rust/src/wl_sandbox.rs`, `rust/src/launch.rs`)

- **flatpak/bwrap/podman/distrobox в исключениях НЕ по недосмотру.** Они создают security-context сами, а у ограниченного клиента этот протокол как раз отобран — вложить одну песочницу в другую не выйдет. Их собственная изоляция строже нашей, пусть работают своим механизмом — но только в `unconfined`: в зоне сырого сокета композитора нет вовсе, ограничение там действует всегда, и flatpak внутри зоны просто получает уже ограниченный сокет. (`rust/src/launch.rs`)

- **Ни одна зона не получает собственный сокет композитора и его IPC — и это держится при перезапусках, а не только при подъёме.** Через `$NIRI_SOCKET` клиент заставляет композитор запустить процесс на хосте, через сырой `wayland-1` набирает команду виртуальной клавиатурой; оба — пути по файлу, сетевому namespace безразличные (LEAK-MODEL §13). Поэтому runtime-каталог каждой зоны — tmpfs с поимённым возвратом записей. Три грабли по дороге: (1) «закрыть» имена, забиндив что-то поверх файла хоста, нельзя — ядро снимает бинд в чужом mount namespace, когда файл под ним удаляют, а композитор при перезапуске пересоздаёт `wayland-1`; (2) биндить из копии каталога хоста, отсоединённой `MNT_DETACH` и удержанной дескриптором, нельзя — `mount(MS_BIND)` из монтирования вне namespace даёт EINVAL (`check_mnt`), поэтому копия остаётся смонтированной на всю жизнь зоны, но под tmpfs 0700 от root зоны, куда программы (пользователь без capabilities) не проходят; (3) снимок при подъёме ломал бы зону после перезапуска pipewire или dbus — inotify-наблюдатель биндит заново то, что хост создал позже, а запрещённое имя не пропускает никогда. `wl-sandbox` поэтому переехал наружу: ограниченный сокет делается на хосте в `vpn-zones/wayland/<зона>/`, каталог своей зоны — единственный такой в ней. (`rust/src/zone.rs` `seal_runtime`, `compositor_private`; `rust/src/launch.rs`; VM — «compositor IPC», «headless sway»)

- **Извлечение app-id из команды полно ловушек.** Шаблон `*=*` для пропуска присваиваний переменных отбрасывал и обычные аргументы со знаком «=» внутри (строка скрипта после `sh -c`) — app-id получался пустым; пропускать надо только настоящие присваивания (`[A-Za-z_]*=*`). Id обязан быть ОДНИМ словом: пробелы разваливали аргумент wl-sandbox на два, и запускалась не та программа (проверено на `sh -c 'echo …'`). `tr -d '\n'` перед обрезкой обязателен: у многострочной команды первая строка пустая, cut отдавал пустоту, и запуск падал с «нужен app-id». (`rust/src/launch.rs`)

## 8. X11 и xwayland-satellite

- **X-сокет хоста не пробрасывается никогда.** В общем X-сервере все клиенты видят окна и ввод друг друга — дыра ровно того размера, который закрывался. Так же считает flatpak: его `--socket=x11` документирован как небезопасный, рекомендуется fallback-x11. (`rust/src/fs_sandbox.rs`)

- **Свой xwayland-satellite поверх ограниченного wayland-сокета.** При разрешении x11 внутри песочницы поднимается отдельный X-сервер, где кроме приложения никого; он подключается к уже ограниченному сокету — обойти security-context через X не выйдет. После старта нужна секунда ожидания: без неё программа стартует раньше появления сокета и падает с «cannot open display». Сателлит обязан работать ВНУТРИ песочницы: его сокет ложится в /tmp, а /tmp там — свежий tmpfs, снаружи в него не попасть. В bash это делала строчка `bash -c '…' ` первым элементом команды bwrap; теперь — внутренняя подкоманда `vpn-zone-core fs-sandbox-x11` (свой путь берётся из `/proc/self/exe`, а /nix/store в песочницу проброшен), так что шелла внутри песочницы больше нет. Гасить сателлит отдельно не надо: `--unshare-pid` делает bwrap init'ом своего pid-namespace, и с выходом программы ядро сносит namespace целиком. (`rust/src/fs_sandbox.rs`)

- **Без разрешения x11 — DISPLAY снять, Electron уводить подсказкой.** Иначе тулкиты видят унаследованный :0, идут на X и падают вместо перехода на Wayland. Electron X не нужен: ему хватает ELECTRON_OZONE_PLATFORM_HINT=auto — проверено на Discord, который без неё падал с «Missing X server or $DISPLAY». (`rust/src/fs_sandbox.rs`)

## 9. D-Bus

- **Сырая сессионная шина = доступ к паролям.** Без фильтра программа через шину дотягивается до Secret Service (то есть до KWallet со всеми паролями), до списка окон и до чужих приложений. xdg-dbus-proxy с --filter пропускает только порталы по имени (`org.freedesktop.portal.Desktop`, `org.freedesktop.portal.Documents`), org.freedesktop.Notifications и org.kde.StatusNotifierWatcher. (`rust/src/fs_sandbox.rs`)
- **Порталы — по имени, а не `org.freedesktop.portal.*`; app id песочницы — в своём пространстве.** Поддерево `portal.*` включает и `org.freedesktop.portal.Flatpak` — портал, чья работа запускать процессы вне песочницы вызывающего, — и любой портал, который хост добавит завтра. Порталы знают программу только по `name=` из `/.flatpak-info` и хранят под ним всё разрешённое человеком (камера, геопозиция, трансляция, фон, ключ Secret-портала), а имя — id программы, который запущенная в зону программа может назвать сама: с голым id она была бы `org.mozilla.firefox` и молча получала разрешённое установленному Flatpak с этим именем. Теперь id — `vpnzone.app.<id>`, Flatpak там не живёт. `Background.RequestBackground` фильтр отклоняет сам: с `autostart` портал пишет автозапуск НА ХОСТЕ, вне всякой зоны, на следующий вход. (`rust/src/zone.rs` `PORTALS`, `rust/src/fs_sandbox.rs` `portal_app_id`, `rust/src/bus_filter.rs` `Door::Background`; найдено аудитом 2026-09-24)

- **Отказ портала — не выход: ссылка просто не откроется.** Запретить `OpenURI` в фильтре нельзя: GLib, получив от портала ошибку, не переходит на `xdg-open`, и программа молча не открывает ссылку. Поэтому фильтр шины песочницы (`bus-filter`) ОТВЕЧАЕТ на вызов сам — дескриптором запроса и сигналом `Response`, — а ссылку открывает `xdg-open` в зоне. (`rust/src/bus_filter.rs`)

- **Сигнал портала — от его уникального имени, не от `org.freedesktop.portal.Desktop`.** GLib с 2.80.1 (CVE-2024-34397) отбрасывает сигнал, чей отправитель — не нынешний владелец имени, на которое подписан клиент. Фильтр узнаёт владельца `GetNameOwner` по своему короткому соединению через тот же прокси; без портала на шине остаётся только известное имя (клиенты «выстрелил и забыл» — `g_app_info_launch_default_for_uri`, `gdbus call` — этого не замечают). (`rust/src/bus_filter.rs` `portal_owner`)

- **Вызов узнаётся по методу, а не по адресату.** До портала доходит и вызов на его УНИКАЛЬНОЕ имя (его отдаёт `GetNameOwner`, а TALK у прокси подразумевает SEE), и вызов без поля интерфейса (шина ищет метод по имени). Фильтр, проверяющий адресат `org.freedesktop.portal.Desktop`, обходился бы одной строкой — проверено опытом. (`rust/src/bus_filter.rs` `door`)

- **DBusActivatable=false в перехваченных ярлыках.** Без этого лаунчер активирует программу через dbus мимо Exec — и весь перехват бесполезен. (`rust/src/desktop.rs`, render_picker)

## 10. .desktop и лаунчеры

- **Генерация .desktop — своим разбором, а не sed.** .desktop — ini с локализованными ключами и экранированием; разбирать его построчно значит однажды получить ярлык с поехавшим Exec. Сначала это был python-скрипт, теперь `rust/src/desktop.rs`; в модуле остаётся тонкая обёртка, подставляющая четыре пути. (`rust/src/desktop.rs`, `module/default.nix` часть 4)

- **В Exec — никаких кавычек и пробелов.** Telegram (и не он один) разбирает Exec наивно, по пробелам, кавычки не снимая: «Zen Browser» разваливался на `Zen` и `Browser"`, и запуск падал с «невозможно выполнить Browser"». В командной строке остаются только слова без пробелов; человекочитаемое имя пикер и диалоги берут из файла меток `.labels` (в списках сброса показывается «Zen Browser», а не ключ вроде com.ayugram.desktop, по которому не догадаешься, о чём речь). (`rust/src/desktop.rs` render_picker, `rust/src/picker.rs` + `rust/src/gui.rs` forget)

- **`--id`: стабильный ключ ярлыка вместо вычисления из команды.** Раньше ключ памяти вычислялся из первого слова команды, и для `Exec=env DESKTOPINTEGRATION=1 AyuGram` получался «env» — все такие программы делили одну память, а в списке сбросов виднелось загадочное «env». Ключ — имя .desktop без расширения; запасной разбор (для запусков мимо ярлыка) пропускает обёртки и присваивания. (`rust/src/desktop.rs` render_picker, `rust/src/picker.rs` `fallback_key`)

- **Ярлыки и пикер обновляются НЕ атомарно — разбирать оба формата аргументов.** При пересборке sync успел отработать раньше подмены профиля, и новый пикер получил ярлыки старого формата (имя программы первым аргументом) — AyuGram перестал запускаться вовсе («невозможно выполнить AyuGram Desktop»). Разбирать оба формата дешевле, чем полагаться на порядок обновления; метка принимается только если дальше в аргументах есть «--», иначе съелась бы команда. (`rust/src/picker.rs` `Args::parse`)

- **Защита от самопоедания генератора.** Файлы с ключом X-VPNZone на вход не берутся; per-zone-клоны отсеиваются ещё и по префиксу имени; симлинки в ~/.local/share/applications (home-manager, Nix) не перезаписываются НИКОГДА, иначе первый же sync затёр бы ярлыки, которые кладёт Nix. Обычные чужие файлы там — с 2026-09-17 перехватываются НА МЕСТЕ (следующий пункт), и только с сохранённым оригиналом: удалять или портить чужую запись sync по-прежнему не может.

- **Чужие записи пользовательского каталога перехватываются на месте, с оригиналом в `.adopted/`.** Раньше инвариант был «чужие файлы не трогать», и через них шли мимо пикера игры Steam, веб-приложения, Wine и — главное — записи `userapp-*`, которые программа пишет, делая себя обработчиком по умолчанию: `mimeapps.list` отправлял в них `http`, `https`, `tg`, и любая ссылка из программы хоста запускала браузер или мессенджер без контейнера, в прямой сети. Тень не помогает: каталога с приоритетом выше нет, а `mimeapps.list` — состояние человека, а не конфигурация. Решение владельца — всё в контейнерах; способ: байты оригинала копируются в `~/.local/state/vpn-zones/.adopted/<имя>` ДО записи, запись переписывается как тень с маркером `X-VPNZone=adopted`, и дальше исходником считается сохранённый оригинал. Нет копии — нет перехвата. Программа переписала свою запись — её новые байты становятся оригиналом, и path-юнит перехватывает заново; окно между перезаписью и повторным перехватом — доли секунды, и в него ссылка открылась бы без контейнера (записано в LAUNCHERS §3.2). `cellward mode off`, `leave` (`interception.userEntries`, файл `user-entries`) или исчезновение программы возвращают оригинал байт в байт: `cleanup` перехваченную запись НЕ удаляет никогда. Скрытая запись этого каталога важна и без `MimeType` — `mimeapps.list` называет её прямо; клонов на зоны у скрытых нет. (`rust/src/desktop.rs` `render_adopted`, `cleanup`, `is_hidden_user_entry`; VM-тест — подтест «user entries») Собственные служебные ярлыки называются vpn-zone-* — генератор их не трогает и сам себя не перехватывает. (`rust/src/desktop.rs`, `module/default.nix` xdg.desktopEntries)
- **Проходы sync идут по одному, а записи пишутся через rename.** path-юнит запускает проход на каждую запись в каталог ярлыков — в том числе на ту, которую делает ручной `cellward sync` или `mode`, — так что два прохода одновременно это обычное дело, а не редкость. Запись через `fs::write` сначала обнуляет файл: второй проход, прочитавший перехваченную запись в этот момент, видел «чужой» файл без маркера и сохранял обрезок КАК ОРИГИНАЛ поверх настоящей копии — `mode off` потом «возвращал» обрезок. А два прохода вперемешку могли и переписать запись, которую соседний только что вернул. Решение: весь проход под `flock` (`.sync/.lock` в каталоге состояния; режим читается уже под ним), а записи, копии и возвраты — через временный файл и rename (`.<имя>.vpn-zone-tmp`, не `.desktop` — ни один проход его не соберёт). Поймано VM-тестом: снимок «оригинала» в тесте успел стать перехваченной записью. (`rust/src/desktop.rs` `write_atomically`, `sync_from`)

- **Автозапуск: ключ — по программе, а не по имени файла; пикер не спрашивает и ничего не запоминает.** Файл автозапуска называет тот, кто его пишет: у Telegram это `telegramdesktop.desktop`, а ярлык — `org.telegram.desktop.desktop`. Ключ по имени файла промахнулся бы мимо закреплений, и закреплённая за зоной программа при входе стартовала бы без сети. Поэтому ключ ищется: `--id` скопированной записи пикера → ярлык с тем же именем → ярлык той же программы → имя файла. Выбранное пикер с `--autostart` запускает без диалога. Невыбранное при `autostart.unassigned = "ask"` (по умолчанию с 2026-09-24) — обычный вопрос пикера с «всегда»; при `offline` и без экрана — ни одного диалога — ни сети, ни контейнера, ни доступов к файлам (своему дому заранее кладётся пустой файл доступов): случайный клик по диалогу при входе — это выбор, которого не было. По той же причине прошлый выбор и общая сеть по умолчанию не берутся — невыбранное становится `offline`, и ничего не записывается в `.last`. Скопированная «в автозапуск» запись нашего пикера разворачивается: обёрнутый дважды пикер спросил бы при входе. `/etc/xdg/autostart` не трогается: одноимённая запись в `~/.config/autostart` выключила бы компонент рабочего стола. (`rust/src/desktop.rs` `sync_autostart`, `autostart_key`; `rust/src/picker.rs` `autostart_plan`; VM-тест — подтест «autostart»)

- **D-Bus-активация идёт мимо ярлыка: нужна тень service-файла, и шине надо сказать о ней.** Программу с `DBusActivatable=true` шина стартует по service-файлу, и `DBusActivatable=false` в тени пикера этого не отменяет — `gapplication launch`, действие уведомления или вызов имени другой программой запускали её в сети хоста. Тень кладётся в `~/.local/share/dbus-1/services/<имя>.service` (каталог пользователя шина читает первым, дубликат дальше по списку пропускает) только для перехваченных записей с корректным именем шины; `SystemdService=` оригинала выбрасывается — с ним шина запустила бы юнит, а не `Exec`. Маркер — КОММЕНТАРИЙ `# X-VPNZone=dbus`: неизвестный ключ шина вправе счесть ошибкой файла. dbus-broker, в отличие от dbus-daemon, каталоги сервисов не отслеживает — новая тень для него не существует до перезагрузки конфигурации, поэтому sync при изменениях зовёт `systemctl --user --no-block reload dbus.service` (без блокировки: sync сам бывает юнитом). (`rust/src/desktop.rs` `render_dbus_shadow`, `dbus_service_exec`, `cleanup_dbus`; VM-тест — подтест «D-Bus activation»)

- **Битые симлинки: «существует ли файл» лжёт.** Проверка существования идёт ПО симлинку и на указывающий в никуда отвечает «нет» — без отдельной проверки sync записал бы файл ПО симлинку, то есть в чужую цель (у home-manager это read-only /nix/store), и весь проход падал с ошибкой. Проверено: именно так и произошло. Правильная проверка занятости пути смотрит на сам симлинк, а не на цель (в python это было `exists() or is_symlink()`, в Rust — `symlink_metadata().is_ok()`). (`rust/src/desktop.rs`, occupied)

- **Писать файлы только при изменении содержимого.** За каталогом ярлыков следит path-юнит: без сравнения он будил бы sync, тот переписывал бы файлы, и цикл не заканчивался бы никогда. (`rust/src/desktop.rs`, write_if_changed)

- **MimeType: per-zone-клонам не давать, picker-ярлыку сохранять.** Иначе клоны начнут перехватывать ассоциации файлов, и «открыть картинку» однажды молча уедет в зону с VPN. В режиме picker наоборот: ярлык один и обязан сохранить ассоциации, иначе программа перестанет быть обработчиком; коды полей (%U, %f) тоже сохраняются — путь долетает до программы через пикер обычным аргументом. (`rust/src/desktop.rs`)

- **В Exec ярлыков — профильные пути cellward и vpn-zone-pick, не store-пути.** Это разрывает зависимость по кругу (cellward зовёт sync, sync подставляет cellward; поэтому же `cellward sync` исполняет vpn-zone-sync через PATH профиля) и ярлыки не протухают при каждом обновлении пакета — иначе после любой пересборки они указывали бы на старый store-путь до следующего sync. Поэтому же оба имени в профиле занимают обёртки, а не бинари крейта (§12). Обратный случай — служебные ярлыки самого модуля (`vpn-zone-gui`): их пишет home-manager и переписывает на каждом switch, там store-путь как раз правильный. (`module/default.nix` vpn-zone-sync-обёртка + `rust/src/cli.rs` sync + `rust/src/tools.rs` runner/picker)

- **Ярлыки игр Steam — дети клиента, а не отдельные программы.** Steam кладёт запись на игру, названную ПО ИМЕНИ ИГРЫ (`PEAK.desktop`, а не `steam_app_*`), с `Exec=steam steam://rungameid/<id>` — искать их по имени файла бесполезно, только по содержимому. Новый `steam` видит `~/.steam/steam.pipe` (обычный FIFO в общем доме — граница netns для него не существует, тот же класс, что nscd-сокет и D-Bus), отдаёт туда URL и умирает, а игру запускает УЖЕ РАБОТАЮЩИЙ клиент — в СВОЕЙ сети. Отсюда правило: **одна программа = один контейнер = одна сеть**, «сеть на игру» невозможна, пока запуском владеет клиент. Поэтому запись, чей аргумент — URL со схемой, которую объявляет (`x-scheme-handler/<схема>`) ДРУГАЯ видимая запись той же программы, — ребёнок: клонов на зоны у неё нет (раньше меню росло как игры × зоны, и каждый клон обещал выбор, которого не будет), а в режиме пикера она перехватывается под id родителя — клик направляет запись работающего клиента, и метку клиента ребёнок не перезаписывает. Записи, которые клиент кладёт прямо в `~/.local/share/applications`, перехватываются на месте — тоже под id клиента (`docs/LAUNCHERS.md` §3.2). **Веб-приложения браузеров — такие же дети**: запись с `--app-id=<id>` (установленный сайт Chromium, Brave, Vivaldi) или `--app=<url>` отдаётся уже запущенному браузеру и открывается в ЕГО сети и профиле, поэтому перехватывается под id видимой записи того же браузера; сама веб-запись родителем браузера не становится, даже если сканер встретил её первой. Нет записи браузера — веб-приложение остаётся своей программой. (`rust/src/desktop.rs` `parents`, `exec_url_schemes`, `claimed_schemes`, `is_web_app_exec`)

- **Ключ ярлыка — без потерь, и хеш в нём менять нельзя.** `sanitize` превращает всё, кроме `[A-Za-z0-9._-]`, в `_`: `Игра.desktop` и `Мама.desktop` давали один ключ `____`, `a b` и `a_b` — один `a_b`. Один ключ — одно закрепление сети, один контейнер, одна метка и один дом песочницы на две программы: вторая молча уходила туда, куда отправили первую. Теперь при потерях к ключу дописывается FNV-1a (`stable_key`), и ключ — неподвижная точка: пикер получает его в `--id` и выводит тот же. Хеш — часть формата состояния: другой алгоритм или другая строка на входе снова «потеряют» все закрепления. Перенос старой памяти — в `sync` под блокировкой, до записи ярлыков с новыми ключами; общий старый ключ не переносится никуда, а сбрасывается — чья это была память, не знает никто, и закрытый вариант — спросить заново. (`rust/src/desktop.rs` `stable_key`, `migrate_keys`)

- **Скрытые обработчики (`NoDisplay=true` + `MimeType`) — это как раз то, через что открываются ссылки и файлы.** Их отсеивали вместе со всем `NoDisplay`, и PDF или ссылка, открытые через `okularApplication_pdf` или `codium-url-handler`, запускали программу мимо пикера — без контейнера и в сети хоста. Теперь такие записи перехватываются, `NoDisplay=true` в тени сохраняется (меню не засоряются), клонов им нет. Но ТОЛЬКО под id видимой записи той же программы: скрытый системный помощник без своей программы в меню (OAuth-колбэк, обработчик URL настроек) остаётся нетронутым, иначе он превращался бы в диалог выбора сети посреди входа в аккаунт. Из нескольких видимых записей одной программы родителем становится та, чей ключ совпадает с именем программы, затем первая по имени — стабильно между проходами. `Hidden=true` — это «удалено», обработчиком не считается. Какую программу запускает запись, определяется разбором `Exec` по правилам спецификации (двойные кавычки, экранирование) и тем же правилом пропуска обёрток, что у `cellward run`; сам `Exec` дальше передаётся нетронутым. (`rust/src/desktop.rs` `is_hidden_handler`, `exec_words`, `exec_program`)

## 11. kdialog и поведение GUI

- **Аргумент с ведущим «-» kdialog принимает за опцию и молча закрывается.** Раньше в именах профилей разрешалась только латиница, и санитизация превращала русское название в строку дефисов — kdialog закрывался без единого слова. Теперь запрещено ровно опасное: разделители пути, пробелы, ведущие дефис/точка; кириллица остаётся кириллицей. Старые каталоги с ведущим дефисом создать уже нельзя, но они могли остаться — меню их просто не показывают. (`rust/src/cli.rs` profile create / sandbox create; `rust/src/picker.rs` `sanitize_name`/`menu_names`; `rust/src/dialog.rs`)

- **Пикер в зоне не видит зон — окно показывает хост.** Состояние проекта от зон спрятано (`zone::hide_project_state`), и пикер, запущенный ссылкой из программы в зоне, предлагал только «Без ограничений» и «Без сети» — даже своей зоны не было (владелец, 2026-09-25). Показывать ему зоны нельзя, а окно, нарисованное зоной, могла бы нарисовать и её программа. Теперь пикер в зоне спрашивает брокер (`broker::pick`), и окно показывает хост (`--from-zone`). Грабли этого окна: оно появляется, когда захочет программа, и забирает фокус — поэтому оно не принимает клавиш и ничего не запускает, пока клавиатура не простоит 1,5 с (одной задержки от появления мало: человек печатает дальше, цифра выбирает строку, Enter соглашается); в нём нет «всегда» и не пишется `.last` — имя ярлыка выбирает зона, и «всегда» для чужого имени решало бы запуски из меню; без окна не решается ничего, даже при закреплении. Брокер сверяет ответ с запросом: та же команда слово в слово, из запертой зоны — только она. (`rust/src/picker.rs` `pick_for_zone`, `rust/src/broker.rs` `handle_pick`, `check_pick`, `window/src/main.rs` `guard`; тесты `a_choice_for_a_zone_*`, `the_window_chooses_where_and_never_what`)

- **Клик по ярлыку работающей программы — «разверни окно», но только у той, что передаёт запуск.** Программа с одним процессом (браузер, мессенджер, Electron) всё равно отдаст команду запущенному экземпляру, и он останется в своей сети — спрашивать её сеть бессмысленно: пикер находит по реестру, где она работает, и запускает туда же с тем же селектором (профиль/песочница) без диалога. Но так было для ВСЕХ, и терминал, однажды открытый в зоне, открывал туда же каждое следующее окно, не давая выбрать (владелец, 2026-09-25): у терминала каждое окно — свой процесс. Какая программа какая, заранее не сказать, поэтому пикер это видит: работающую программу, не замеченную в передаче, он спрашивает, с её сетью на выборе, и запуск в ТУ ЖЕ сеть запускает ребёнком и смотрит `HANDOVER_WINDOW` (5 с). Ушла за это время с успехом — передала запуск: `.handover/<ключ>`, и дальше клик по ней, пока она работает, снова «разверни окно». Запуск в другую сеть не смотрится: там `cellward run` предупреждает, а отмена предупреждения тоже выходит с успехом; изнутри зоны тоже — запуск делегируется, и `run` возвращается сразу (§13). Ошибиться пикер может только в безопасную сторону — программу, что сама уходит в фон, он примет за передающую, то есть поведение будет прежним; а две живые записи одной программы разом (два контейнера одного браузера, или ошибка) снимают метку. (`rust/src/picker.rs` `net_step`, `watch_handover`, `launch_asked`; тест `a_running_program_is_asked_until_it_is_seen_handing_over`)

- **Сеть и контейнер закрепляются порознь.** Сначала закрепление хранило пару «сеть+контейнер», и «Всегда» в первом окне намертво фиксировало заодно и второе — неверно: это независимые оси. Теперь два файла (.pinned и .pinnedprofile), диалог показывается только для незакреплённой оси. В .pinnedprofile значение «всегда основной» — сентинел `__main__`: пустую строку не отличить от «не закреплено». (`rust/src/picker.rs` `profile_pin_is_valid`) С 2026-09-26 сеть — у контейнера, а не у программы (`docs/PERMISSIONS.md` §11.8): `.pinned` при первом взгляде переносится в сеть контейнера программы (`container::migrate_pins`), «Всегда» в основном доме переводит программу в контейнер основного дома этой сети (`main-<сеть>`).

- **Закреплённая сеть + незакреплённый контейнер — отдельное окно контейнера.** Пункт «Сменить контейнер» живёт в окне выбора сети; когда сеть закреплена и окно не показывается, попасть в выбор контейнера было неоткуда — поэтому он спрашивается своим окном. Так возможно «сеть всегда одна, контейнер каждый раз выбираю». (`rust/src/picker.rs` `NetStep::Pinned`)

- **Запоминать ВЫБОР, а не переменную profile.** У песочницы profile пуст (она живёт отдельным флагом fssand/sandbox), и запись «как есть» превращала её в «основной» — выбор выглядел не сохранившимся. В .lastprofile пишется селектор (`__fs__`, имя контейнера — до 2026-09-26 у песочницы `sb:имя`); одноразовые контейнеры (`__tmp__`, `tmpjoin:`) не запоминаются — помнить их незачем. (`rust/src/picker.rs` `Container::selector`)

- **«Сменить контейнер» — это ВТОРОЙ ПРОХОД пикера, и выбор надо донести переменной.** Пункт живёт в окне сети, а после ответа надо снова спросить сеть — пикер запускает сам себя (`exec` с `VPN_ZONE_ASK=1`). Через файл `.lastprofile` выбор не донести весь: одноразовые контейнеры (`__tmp__`, `tmpjoin:`) туда намеренно не пишутся, и они терялись начисто — человек выбирал «🗑 Новый временный», а программа открывалась в прежнем ПОСТОЯННОМ контейнере (для песочницы это прямая потеря изоляции). Поэтому выбор едет ещё и в `VPN_ZONE_PROFILE`, пустой («Основной») — как `__main__`; переменная читается первым делом и тут же убирается из окружения, иначе уехала бы в саму программу и ссылка, открытая из неё, унаследовала бы чужой контейнер. Во втором проходе она сильнее и закрепления, и `.lastprofile`. (`rust/src/picker.rs` `container_without_dialog`, `reexec`)

- **Мёртвые закрепления снимать.** `cellward rm` снимает закрепления, указывающие на удаляемую зону — иначе программа осталась бы привязана к несуществующей сети и молча падала бы при каждом запуске. Пикер дополнительно проверяет, что закреплённая зона/профиль ещё существуют, и сбрасывает битые записи. (`rust/src/cli.rs` rm; `rust/src/picker.rs` `pin_is_valid`)

- **Вопрос о контейнере задаётся всегда, даже когда профилей ещё нет.** Сначала диалог показывался только при наличии профилей — и о функции невозможно было узнать, не читая справку: система молча решала, что контейнер не нужен. Пункт «Основной» есть всегда, рядом — «Новый профиль…»/«Новая песочница…», чтобы завести контейнер прямо из диалога. (`rust/src/picker.rs` `profile_menu`)

## 12. Bash внутри Nix: экранирование

- **Историческое: `''${var:+…}` с кавычками внутри не работает.** Кавычки в такой подстановке остаются литеральными символами, аргументы разъезжаются — bwrap пытался ВЫПОЛНИТЬ номер дисплея («execvp :149»). В bash единственным надёжным способом собирать опциональные аргументы были массивы. С переездом песочницы в крейт этот код исчез: аргументы — `Vec<OsString>`, экранировать нечего. Правило остаётся верным для любого будущего опционального аргумента, который однажды понадобится в shell. Сегодня опциональные аргументы диалогов собираются так же — `Vec<OsString>` (`rust/src/picker.rs`, `rust/src/gui.rs`). (`module/default.nix`; было — vpn-fs-sandbox)

- **Историческое: printf вместо heredoc в середине Nix-строки.** Строка в реестр добавлялась printf'ом: многострочная переменная с закрывающей кавычкой в нулевой колонке сбила бы снятие общего отступа в Nix indented string и разломала бы heredoc справки выше по файлу. С переездом CLI в крейт этого кода нет — запись в реестр пишет `rust/src/registry.rs`, а справка живёт строковой константой. Правило верно для любого будущего многострочного текста в shell. Заодно родственная грабля из GUI: в Nix-строке `'' … ''` обратный слэш ничего не экранирует, поэтому «\n» в текстах диалогов доезжали до kdialog двумя символами — при переносе в Rust они сохранены буквально, иначе диалог выглядел бы иначе. (`module/default.nix`; было — cellward run и vpn-zone-remove-gui; сейчас — `rust/src/gui.rs`)

- **Абсолютные пути ко всем инструментам.** Часть кода исполняется внутри namespace, где PATH может быть каким угодно — все вызовы через ${pkgs.…}/bin/…. В обёртках это по-прежнему интерполяция, в крейте — манифест (ниже). (`module/default.nix`, let-блок)

- **Скомпилированному бинарю пути передаются МАНИФЕСТОМ, а не интерполяцией.** Единственное, на чём стоял shell-скрипт, — подстановка store-путей Nix'ом; у бинаря её нет, а абсолютные пути обязательны (см. выше). Поэтому Nix пишет их в маленький плоский JSON (`writeText`), а двухстрочная обёртка в `home.packages` показывает на него ЕДИНСТВЕННОЙ переменной `VPN_ZONE_TOOLS` и делает exec. Парсер JSON — свой, без serde: формат наш и плоский, а файл читается на старте каждой запускаемой программы. Отсутствие ключа — громкая ошибка с именем ключа (обёртка и бинарь разъехались поколениями), а не молчаливый дефолт: угадав, можно запустить программу не в той сети. Ключи перечислены в `rust/src/tools.rs`; их же грепает смоук, чтобы проверять то, что поедет пользователю. (`rust/src/tools.rs`, `module/default.nix` часть 3)

- **Два `bin/vpn-zone` и два `bin/vpn-zone-pick`: в крейте и обёртками — в профиль кладётся только по одному.** Эти два имени занимают обёртки (`writeShellScriptBin`), потому что по этим путям их зовут ярлыки, GUI и сам CLI. Такие же бинари есть и в крейте, и положи мы крейт в `home.packages` целиком — buildEnv профиля упал бы на collision. Поэтому из крейта в профиль уходит symlink-набор `vpn-zone-helpers` (только `vpn-zone-core` и `vpn-zone-seccomp`), а CLI и пикер — через обёртки. Третий бинарь, `vpn-zone-gui`, тоже приходит в профиль обёрткой: `.desktop`-записи зовут его store-путём (их пишет home-manager и пересобирает на каждом switch, так что протухнуть путь не может), но окна открывают и по имени — конфигуратор и человек из терминала; пока обёртки не было, такой запуск падал с ENOENT. После переименования обёртка CLI в профиле — `cellward`, а `vpn-zone` и `cw` — её же другие имена; обёртка окон — `cellward-gui`, и `vpn-zone-gui` — тоже её имя. (`module/default.nix`, часть 3 + home.packages + xdg.desktopEntries)

- **Историческое: `#include "…"` не работает из /nix/store.** Заголовки ищутся относительно исходника, а тот лежит в read-only store, где ничего сгенерировать нельзя — исходник копировался в каталог сборки рядом со сгенерированными wayland-scanner заголовками. Деривации больше нет (C поглощён крейтом, см. §7), но правило верно для любой будущей C-сборки в модуле. Актуальная замена этой грабли: libwayland в крейте НЕ линкуется — фича `wayland-backend/client_system` выключена по умолчанию, wayland-client говорит по проводному протоколу сам, и `buildInputs` деривации остаются без `pkgs.wayland`. (`module/default.nix`, деривация vpn-zone-rust)

## 12б. Контейнер: сеть и декларативная сторона

- **Проверка «одна личность — одна сеть» стоит ДО создания чего-либо.** `cellward run` отказывает контейнеру, привязанному к другой сети (I1), и любому контейнеру, чьи программы уже работают в другой сети (I2), раньше, чем появится одноразовый каталог, обёртки и запись в реестре: отказ после `mkdtemp` оставил бы мусор в `/tmp`, а после записи в реестр — «призрака», которого пикер принял бы за работающую программу. Отказ говорит, как выйти (`cellward container set …`), и показывается диалогом: stderr ярлыка не читает никто. (`rust/src/launch.rs` `identity_refusal`, `rust/src/container.rs` `refusal`)

- **Именованная песочница искалась в реестре по селектору, а не по каталогу.** У запусков песочницы не было контейнера данных, и их записи лежали в `.running/__main__` вперемешку со всем остальным; «где сейчас работает sb:work» отвечало только третье поле записи. С одним именем на контейнер (2026-09-26) у каждого контейнера свой каталог реестра, а записи прежнего вида (`sb:<имя>` в `__main__`) читаются, пока живы. (`rust/src/container.rs` `running_network`)

- **Привязанная сеть контейнера отвечает на вопрос о сети раньше закрепления сети.** Сеть — часть личности контейнера, а закрепление сети у программы — только память; при конфликте закрепление устарело. Сильнее только работающий экземпляр передающей программы (клик = «разверни окно») и явный `VPN_ZONE_ASK`. (`rust/src/picker.rs` `net_step`)

- **Nix сильнее локального, и CLI это говорит, а не молчит.** Модуль пишет `~/.config/vpn-zones/declared/` (ссылки в store, только чтение); рантайм читает оттуда первым. Запись локального файла при заданном в Nix значении ничего бы не изменила — поэтому `write_setting`, `container set` и `container assign` отказывают с «задано в Nix», вместо того чтобы «успешно» не сработать. Назначение программы в Nix сильнее закрепления пикера. (`rust/src/cli.rs` `setting`, `rust/src/container.rs`)

- **Декларативные сертификаты проверяются при СБОРКЕ.** Модуль собирает каталог `<sha256>.pem` через openssl и падает, если в файле больше одного сертификата или это не УЦ: плохой корень должен ломать `home-manager switch`, а не молча доезжать до контейнера. Такой каталог только для чтения, поэтому бандлу нужен собственный каталог `trust/` контейнера (его создаёт запуск), а отпечатки берутся из имён файлов — считать SHA-256 в крейте незачем. (`module/default.nix` `trustDir`, `rust/src/launch.rs` `trust_of`)

- **Выдача пути — список разрешённого, и проверяется разрешённый путь.** Выданный песочнице каталог биндится bwrap-ом, а bwrap идёт по symlink: `~/games → ~/.local/state/vpn-zones` отдал бы программе ключи всех зон, если бы проверялось только написанное. Поэтому путь проверяется дважды — как написан и после `canonicalize`, — и биндится разрешённый. И это список разрешённого (дом и `/mnt`, `/media`, `/run/media`, `/srv`), а не опасного: в `/run/user` сокет D-Bus в обход прокси, в `/tmp` сокеты X11, и перечень опасного однажды недосчитается сокета. Проверка стоит и в CLI (понятный отказ), и в `fs-sandbox` при каждом запуске — файл `paths` лежит в каталоге песочницы и мог быть изменён руками. (`rust/src/container.rs` `forbidden_path`, `rust/src/fs_sandbox.rs` `run`; смоук — «выданный каталог»)

- **Объединение контейнеров ничего не разыменовывает и не пишет в существующий каталог конфликтов.** Объединение работает вне песочницы, а дома принадлежат программам: программа из `<в>` может заранее положить в свой дом `.merged-from-<из>` как ссылку на `~/.ssh` или `~/.config/autostart`, и копирование конфликтов прошло бы сквозь стену. Поэтому каталог конфликтов всегда новый (`-2`, `-3`…), symlink в назначении — занятое имя, а не каталог, в который спускаются, и symlink из источника копируется как ссылка. Пометки удаления оверлея — символьные устройства — пропускаются: удалённый в `<из>` файл, который есть в нижнем слое, в `<в>` остаётся видимым, объединение только добавляет. (`rust/src/container.rs` `merge`, `merge_tree`, `fresh_aside`; тест CLI «a merge keeps what the target has»)

## 12а. Доверенные сертификаты контейнера

- **Переменные окружения указывают на СИСТЕМНЫЙ путь, никогда на путь контейнера.** `SSL_CERT_FILE`, `NIX_SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `GIT_SSL_CAINFO`, `NODE_EXTRA_CA_CERTS` внутри контейнера — это `/etc/ssl/certs/ca-certificates.crt`, а содержимое, отличное от хоста, приходит только из монтирования. Переменные утекают: программа в контейнере может сделать `systemctl --user import-environment`, и с этой минуты их унаследует любой пользовательский сервис. С системным путём утечка безвредна — снаружи этот путь означает обычный бандл хоста; VM-тест проверяет это, сначала убедившись, что импорт действительно случился. (`rust/src/trust.rs` `bind_bundle`)

- **Слоты `.pki` и `.mozilla` у контейнера с доверием накладываются всегда — даже если на хосте таких каталогов нет.** Оверлей накладывается только на существующий нижний каталог (§5). На доме без `~/.pki` вызов `certutil -d sql:$HOME/.pki/nssdb` внутри контейнера создал бы базу В НАСТОЯЩЕМ ДОМЕ — и Chromium хоста доверял бы чужому корню с этой минуты. Поэтому недостающие нижние каталоги создаются пустыми (0700) до наложения, а база пишется только под слотом из списка, который `mount_profile` вернул как реально смонтированный, или под домом именованной песочницы. Остальные базы (`~/.zen` не входит в XDG-слоты) пропускаются с предупреждением, которое называет выход — контейнер со своим домом. (`rust/src/profile.rs` `TRUST_SLOTS`, `rust/src/trust.rs` `sync_nss`, `under_any`)

- **Бандл биндится поверх файла, в который разрешается цепочка, — на NixOS это файл в store.** Все известные пути бандла (`/etc/ssl/certs/ca-certificates.crt`, `ca-bundle.crt`, `/etc/pki/tls/certs/ca-bundle.crt`, …) на NixOS ведут через `/etc/static` в ОДИН файл `nss-cacert`; `mount(2)` всё равно следует симлинкам, а разрешение руками (`sys::link_target`, как для resolv.conf, §3) даёт биндить каждый настоящий файл один раз. Заодно бинд достаёт программы, которые называют `${cacert}/etc/ssl/certs/ca-bundle.crt` напрямую, и NSS — в nixpkgs `libnssckbi.so` это симлинк на `p11-kit-trust.so`, который читает тот же файл. bwrap биндит `/nix/store` рекурсивно, поэтому именованная песочница видит тот же бинд. (`rust/src/trust.rs` `bind_targets`)

- **Источник бинда — tmpfs поверх каталога `trust/` самого контейнера.** Файлу бандла нужно место, видимое только этому запуску: `/tmp` зоны — та же файловая система, что у хоста, и файл там увидел бы кто угодно. Сертификаты уже прочитаны в память, поэтому каталог накрывается tmpfs, бандл пишется туда (0444) и биндится, а сверху — перемонтирование только для чтения. (`rust/src/trust.rs` `bind_bundle`)

- **Доверие включает сам каталог `trust/`, даже пустой, и оно заставляет запуск взять свой mount namespace.** После `trust reset` у контейнера-оверлея из баз NSS уходит его корень только изнутри следующего запуска (писать в верхний слой смонтированного оверлея снаружи нельзя) — это и делает пустой каталог: штамп в базе говорит, что было поставлено, и лишнее снимается. Базы именованной песочницы — её каталог на диске, их CLI приводит в порядок сразу. Бинд без своего mount namespace лёг бы в namespace зоны, и его увидел бы соседний контейнер той же зоны, — поэтому каталог доверия, как и слой данных, всегда даёт `unshare --mount` (в direct — свой userns). (`rust/src/launch.rs` `entry_argv`, `trust_of`)

- **Бандл не наложился — запуск остановлен; база NSS не доказана своей — только предупреждение.** Программа, которая по ожиданию человека доверяет корню контейнера, а на деле молча нет, — сломанный запуск, и «запустить без слоя» не должно быть путём, на который можно попасть случайно. База NSS — второй путь к тому же корню для части программ, и её пропуск не отнимает первый. `cellward trust add` принимает ровно один сертификат с `basicConstraints CA:TRUE`: бандл, добавленный «как сертификат», протащил бы каждый корень из себя, а лист корнем быть не может. Основной профиль сертификатов не держит: его базы — это базы хоста. (`rust/src/trust.rs`, `rust/src/cli.rs` `trust_add`)

## 13. systemd

- **Делегирование запуска через systemd-run --user.** systemd --user живёт в корневом namespace, его сокет виден изнутри зоны, и запущенная им команда стартует снаружи — оттуда переход в любую зону разрешён. Графическое окружение у него своё, полное (WAYLAND_DISPLAY, DBUS, XDG_RUNTIME_DIR) — проверено. Тем же способом «Прямой интернет», выбранный изнутри зоны, становится действительно прямым, а не наследует её сеть. Метки: VPN_ZONE_CURRENT помечает потомков зоны, VPN_ZONE_DELEGATED предотвращает повторное делегирование. (`rust/src/launch.rs`)

- **VPN_ZONE_DELEGATED снимается сразу после проверки — в программу он ехать не должен.** Он жил в окружении делегированного запуска до конца: браузер, открытый ссылкой из мессенджера в зоне, нёс `VPN_ZONE_DELEGATED=1`, и следующая ссылка, нажатая уже В НЁМ, пропускала делегирование и умирала в `nsenter` с «reassociate to namespaces failed» — ровно та ошибка, ради которой делегирование и существует. Метка одноразовая: она защищает от петли ОДИН запуск, а не всё дерево процессов. (`rust/src/launch.rs` `run`)

- **`direct` — не особый случай запуска, а сеть без namespace.** Пикер для «Прямого интернета» сам становился командой, и всё, что по дороге добавляет `cellward run`, молча терялось: выбранный (закреплённый, заданный по умолчанию) контейнер или песочница — программа получала весь `$HOME`; ограничение композитора, хотя оно включено по умолчанию; запись в реестре — предупреждение «уже запущена в другой сети» программ в direct не видело; а из ЗАПЕРТОЙ зоны его собственный `systemd-run` проходил мимо замка. Теперь пикер отдаёт direct в `cellward run direct`, как любую сеть, и отличается ровно шаг namespace: зоны, в которую входить, нет. Контейнеру там user namespace даёт `unshare --user --map-current-user --keep-caps --mount --propagation private`: uid отображён сам в себя (программа видит свой `$HOME`), `--keep-caps` нужен по той же причине, что `nsenter --keep-caps` в зоне (§1) — `profile-run` монтирует слой и сбрасывает права до старта программы; netns не создаётся — direct и есть сеть хоста. Без контейнера и песочницы direct-программа — обычный процесс хоста и `VPN_ZONE_CURRENT` не получает, иначе всё, что она запускает, шло бы в обход через systemd. Имена `direct` и `offline` `cellward add` не принимает. (`rust/src/launch.rs` `entry_argv`, `rust/src/picker.rs` `launch`, `rust/src/cli.rs` add; смоук — шаг 6а)
- **`direct` переименован в `unconfined` (2026-09), и старое имя — синоним, который читается везде и не пишется нигде.** Имя должно говорить, что вокруг программы нет ничего от зоны: ни VPN, ни своего резолвера, шина сеанса, `systemd --user` и X — хоста. Старое имя могло остаться в закреплениях, в `.last`, в настройке `default`, в `container.conf`, в Nix и в записях реестра уже запущенных программ, поэтому нормализация стоит на каждом входе: разбор `cellward run`, `Network::parse`, чтение памяти пикера, `registry::parse_record`, `cellward default`. Грабля переименования — зона, которую пользователь сам назвал `unconfined` до того, как имя стало встроенным: `cellward run unconfined` молча ушёл бы в сеть хоста мимо её VPN. Такой запуск отказывается (и по старому имени тоже), пикер и GUI её не предлагают, `status --json` не показывает второй `unconfined`, `doctor` называет её `fail`, `cellward rm` удалять её не мешает. (`rust/src/launch.rs` `network_name`, `run`; `rust/src/doctor.rs`; тест `a_zone_left_with_the_name_unconfined_is_refused_not_left_behind`)
- **`cellward kill` сначала замораживает, потом опускает зону, потом убивает — и никогда не трогает сеть хоста.** `down` забирает у зоны сеть, но программы, запущенные в неё, живут в своих cgroup (скоуп лаунчера, `systemd-run`) и переживают остановку юнита; программа удалённого доступа осталась бы с тем, что уже получила. Поэтому все процессы сетевого namespace зоны получают `SIGSTOP` (не перехватывается) проход за проходом, пока проход не найдёт новых — форк между проходами ловит следующий; только потом `systemctl stop`, затем `SIGKILL` замороженным. Процессы самого юнита (держатель, заглушка app-ns, pasta, прокси) исключаются по cgroup и по pid заглушки: замороженный держатель задержал бы остановку до таймаута systemd (90 с). Если проходы кончились, замороженное всё равно убивается — оставить процессы в `SIGSTOP` навсегда хуже. Сигналы — через pidfd, открытый после проверки namespace, и namespace проверяется ещё раз уже с pidfd в руках: переиспользованный pid не получит сигнал. И главное: если namespace «зоны» совпадает с сетью самого `vpn-zone` (подменённый или устаревший `zone.pid`, указавший на процесс хоста), команда отказывается ДО любого сигнала — иначе «всё в этом namespace» было бы всей сессией. (`rust/src/kill.rs`; тест `kill_refuses_what_is_not_a_zone_of_its_own`, VM — «cellward kill»)
- **Отобрать выданный каталог у уже запущенной песочницы можно только из user namespace, которому принадлежат её монтирования, и только снимая бинд до конца.** Строка в `paths` для работающей программы ничего не значит: бинд уже в её mount namespace. Поэтому `revoke` и истечение срока (`cellward container expire`, его зовёт пользовательский таймер в конце срока) входят в mount namespace каждой запущенной программы песочницы и делают `umount2(MNT_DETACH)`. Две грабли, обе пойманы смоуком: (1) bwrap монтирует в первом user namespace, а программу переводит во второй, вложенный (чтобы отобразить uid песочницы), — `setns` в mount namespace из user namespace самой программы отказывает, входить надо во ВЛАДЕЛЬЦА, его отдаёт `ioctl(NS_GET_USERNS)` на дескрипторе mount namespace; (2) по одному пути может лежать больше одного бинда — снятый верхний открывал нижний, и программа видела каталог дальше, поэтому `umount2` повторяется, пока не откажет. Отмонтирование не отнимает уже открытое (дескриптор, рабочий каталог внутри) — для жёсткого конца `cellward kill`. Выдача с истёкшим сроком при этом отсутствует для любого нового запуска с той же секунды, даже если таймер не сработал. (`rust/src/grants.rs`; смоук — «истёкший срок забирает каталог и у запущенной программы»)

- **Пересборка ярлыков сразу после активации home-manager.** Без `home.activation` после linkGeneration порядок случайный: таймер или path-юнит могли отработать ДО подмены профиля — ярлыки оставались в старом формате при новом пикере, и запуск программ ломался до следующего срабатывания таймера. Триггеры пересборки: активация, вход в сессию, каждые 30 минут, изменение каталогов с .desktop (после nixos-rebuild там появляются новые программы). (`module/default.nix`, home.activation.vpnZoneSync + timer/path-юниты)

- **Ярлык при опущенной зоне — поднять её самому.** Это ожидаемое поведение, а не ошибка: `run` сам стартует vpn-zone@<имя>.service и ждёт файла ready. Зона переживает выход из графической сессии — живёт, пока её не погасят. (`rust/src/launch.rs` + юнит vpn-zone@ в `module/default.nix`)
