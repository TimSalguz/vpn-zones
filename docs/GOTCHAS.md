# GOTCHAS — накопленные грабли vpn-zones

Это спецификация накопленного поведения проекта: систематическая выгрузка всех неочевидных фактов («граблей») из комментариев и кода `module/default.nix`, `module/vpn-profile-run.py`, `module/vpn-zone-sync.py`, `module/wl-sandbox.c` — для будущего переписывания ядра на Rust. Каждая запись должна превратиться либо в тест, либо в явно сохранённый инвариант нового кода: ни одна не должна потеряться.

## 1. User namespaces и capabilities

- **Двойной маппинг uid: иначе либо нет capabilities, либо чужой uid.** Внутри зоны нужен uid 0 — capabilities теряются при execve, если uid ненулевой (проверено: с identity-маппингом CapEff=0), и ядро не даёт создать интерфейс. Второй диапазон (`--map-users=<uid>:<uid>:1`) отображает настоящий uid в себя, чтобы приложение, вошедшее через `nsenter --preserve-credentials`, работало под твоим uid и видело $HOME — ровно как podman в режиме keep-id. (`module/default.nix`, шапка + zoneHolder)

- **subuid — источник «root» зоны.** uid 0 внутри берётся из первого диапазона /etc/subuid (newuidmap имеет на это cap_setuid). Нет диапазона — rootless-зона невозможна в принципе; это проверяется явно с внятной ошибкой. (`module/default.nix`, zoneHolder)

- **Из namespace нельзя перейти в другой namespace.** Процесс, уже находящийся в user+net namespace, не может войти в другой: «nsenter: reassociate to namespaces failed». Симптом: клик по ссылке в Telegram-в-зоне открывал пикер, а браузер не появлялся вовсе, причём «Прямой интернет» молча наследовал сеть зоны. Решение — делегировать запуск наружу (см. раздел systemd). Следствие для запертой зоны (lock/no-escape): повторно войти даже в СВОЮ зону нельзя — аргументы выбора сети/профиля отбрасываются и команда исполняется на месте через exec; профиль отбрасывается тоже, потому что прав смонтировать слой внутри зоны уже нет. (`module/default.nix`, vpn-zone run)

- **`nsenter --keep-caps` обязателен для монтирования профиля.** Без него CapEff обнуляется при входе в user namespace зоны, и смонтировать overlay-слой нечем. (`module/default.nix`, vpn-zone run)

- **mount(8) не работает без root даже при CAP_SYS_ADMIN.** Утилита из util-linux при запуске не от root пытается сбросить привилегии и падает с «drop permissions failed», хотя права на монтирование есть (получены от nsenter --keep-caps). Прямой вызов libc.mount такой проверки не делает — монтировать надо системным вызовом. (`module/vpn-profile-run.py`)

- **Ambient capabilities переживают execve — чистить явно.** Без `prctl(PR_CAP_AMBIENT, PR_CAP_AMBIENT_CLEAR_ALL)` перед запуском Chrome унаследовал бы CAP_SYS_ADMIN внутри namespace. Права нужны ровно на монтирование, дальше снимаются. (`module/vpn-profile-run.py`)

## 2. Сеть, маршрутизация, pasta

- **pasta: `-I hostif` против столкновения имён.** По умолчанию pasta копирует имя выходного интерфейса хоста; если хост сам под VPN и интерфейс называется awg0, внутри зоны случилось бы столкновение имён с туннелем зоны. Имя задаётся явно. (`module/default.nix`, zoneHolder)

- **Зона — отдельный форкнутый процесс, чтобы pasta могла подключиться.** pasta остаётся в сети хоста и цепляется к зоне снаружи по `--netns /proc/<pid>/ns/net`, поэтому net+mount namespace создаётся отдельным процессом (`unshare --net --mount --fork`), а не в том же, где pasta. (`module/default.nix`, zoneHolder)

- **Маршрут pasta разбирается по ключевым словам, не по позициям.** У pasta default-маршрут имеет вид «default dev hostif scope link» (без via), у обычной сети — «default via 192.168.1.1 dev enp4s0 …». Позиционный разбор во втором случае ловил слово «link» вместо имени интерфейса — маршрут до VPN-сервера не добавлялся вовсе (проверено). Перед разбором надо дождаться, пока pasta вообще создаст default-маршрут — до этого добавлять маршрут до endpoint некуда. (`module/default.nix`, zoneInit)

- **Маршрут до VPN-сервера — мимо туннеля, ошибку не глушить.** Иначе петля: пакеты туннеля заворачиваются в туннель. Имя endpoint резолвится, пока DNS ещё хостовый; при отсутствии шлюза маршрут ставится `scope link` на выходной интерфейс. Ошибка добавления печатается — молчать нельзя, без этого маршрута зона просто не работает. (`module/default.nix`, zoneInit)

- **Оффлайн-зона: отсутствие маршрута вместо запрета.** Особая зона — только loopback, без туннеля и без pasta: программа работает, но маршрута наружу физически не существует. Это основа политики «интернет не выдаётся, пока его явно не дали». Такая зона — пустой namespace, создаётся по требованию и в конфиге не хранится; `direct` и `offline` — встроенные варианты пикера, а не зоны, их нельзя удалить и они не показываются в GUI удаления. (`module/default.nix`, zoneInit, vpn-zone rm, vpn-zone-remove-gui)

- **Один приватный ключ нельзя поднимать дважды.** Сервер помнит для ключа ровно один endpoint, второе соединение перебивает первое — оба начинают рваться. Нельзя поднимать зону из конфига, уже поднятого системным туннелем, и нельзя делить один файл между двумя зонами: нужны разные ключи. (`module/default.nix`, шапка)

- **Kill switch = процесс-держатель + KillMode.** Namespace живёт, пока жив `exec sleep infinity` в конце zoneInit: умер держатель — исчезла зона и сеть у всего, что в ней работало. На уровне systemd KillMode=control-group (по умолчанию) гасит вместе с зоной и pasta, и всё запущенное внутри. (`module/default.nix`, zoneInit + юнит vpn-zone@)

- **gc — точные критерии, а не «убить всё осиротевшее».** Первая версия gc погасила живую зону, потому что смотрела только на zone.pid. Теперь: процессы в cgroup vpn-zone@ не трогаются вовсе (ими управляет юнит); pasta убивается только если netns из её командной строки (/proc/N/ns/net) мёртв; чужие bwrap-песочницы не трогаются — в них работают программы. (`module/default.nix`, vpn-zone gc)

## 3. DNS

- **nsncd — реальная утечка DNS мимо туннеля.** В NixOS работает nsncd (сокет /run/nscd/socket), и glibc ходит за именами к нему, а не к DNS из resolv.conf; демон живёт в сети хоста. Проверено на живой зоне: `getent` отвечал при RX=0 на awg0 — запрос уходил в обход VPN, и подмена resolv.conf этого не лечит. Лечение: tmpfs поверх /run/nscd (или /var/run/nscd) внутри зоны — glibc не находит сокет и идёт напрямую к серверам из resolv.conf через туннель; у остальной системы nsncd работает как раньше. (`module/default.nix`, zoneInit)

- **resolv.conf зоны — mount --bind, видимый только внутри.** DNS из конфига пишется в файл зоны и бинд-монтируется поверх /etc/resolv.conf; без этого запросы уходили бы к резолверу хоста мимо туннеля — самая частая утечка. У остальной системы /etc/resolv.conf прежний. (`module/default.nix`, zoneInit)

- **В bwrap-песочнице не резолвятся имена без /run/systemd/resolve.** /etc/resolv.conf — симлинк в /run/systemd/resolve, а сам /run в песочницу не пробрасывается; нужен отдельный `--ro-bind-try /run/systemd/resolve`. (`module/default.nix`, vpn-fs-sandbox)

## 4. Конфиги WireGuard/AmneziaWG

- **awg setconf понимает только ключи протокола.** Address/DNS/MTU/Table/PreUp/PostUp/PreDown/PostDown/SaveConfig — указания wg-quick: их надо вычистить из файла (иначе setconf падает на первой же такой строке) и применить руками: адрес — первый из списка через запятую, MTU по умолчанию 1420. (`module/default.nix`, zoneInit)

- **CRLF от Amnezia.** Amnezia отдаёт .conf в формате Windows — проверено на настоящем файле: 21 строка с \r. «\r» попадает в конец значения, и зона падает на первой команде: `ip addr add 10.8.1.10/32<CR>` → «inet prefix is expected rather than "10.8.1.10/32"» — ошибка выглядит бессмысленно, потому что возврат каретки в сообщении не виден. Чистить надо и при `vpn-zone add`, и повторно в zoneInit: конфиг могли положить в каталог зоны руками. (`module/default.nix`, vpn-zone add + zoneInit)

- **Пустые параметры I1…I5 валят setconf целиком.** Свежая Amnezia кладёт параметры пакетов-приманок I1…I5 и заполняет не все: получается «I2 = ». awg setconf на такой строке падает целиком — «Line unrecognized: `I2='» — и зона не поднимается вовсе (проверено на двух реальных конфигах: старый набор Jc/S/H работал, новый с I1…I5 — падал). Выбрасывать только строки с пустым значением: заполненные параметры обфускации обязательны, без них сервер не ответит. (`module/default.nix`, zoneInit)

- **Конфиг — копия mode 600, не симлинк.** Файл с приватным ключом должен пережить перемещение и удаление исходника (`install -m 600 /dev/null`, затем запись). При удалении зоны копия стирается — восстановить ключ неоткуда, поэтому GUI удаления обязан переспрашивать вторым шагом. (`module/default.nix`, vpn-zone add + vpn-zone-remove-gui)

- **Первое рукопожатие — главный признак «конфиг живой».** Зона через ~4 с печатает в журнал, прошло ли рукопожатие (`awg show awg0 latest-handshakes`); GUI-добавление ждёт 6 с и сразу сообщает, живой ли конфиг — ради этого ответа зону обычно и создают («какой из моих .conf ещё работает?»). (`module/default.nix`, zoneInit + vpn-zone check + vpn-zone-add-gui)

- **`awg show` изнутри под обычным uid молчит; «нет данных» ≠ «нет рукопожатия».** awg show требует прав на netlink, а программы и `vpn-zone status` заходят в зону под обычным uid — состояние туннеля было недоступно вообще. Поэтому зона сама изнутри (где права есть) пишет зеркало состояния в файл каждые 5 с, атомарно через mv. `vpn-zone check` при отсутствии файла зеркала (зона поднята старой версией) не объявляет живой туннель мёртвым, а просит перезапустить зону — отдельный код выхода. (`module/default.nix`, zoneInit + vpn-zone status/check)

## 5. Overlayfs, профили, контейнеры

- **Хранилище профилей в `.local/state` — не вкусовщина.** Верхний слой overlayfs не может находиться на overlayfs. Пока хранилище лежало в .local/share, первые два каталога монтировались, а на .cache и дальше ядро отвечало EINVAL: их upperdir оказывался уже накрыт предыдущим слоем. .local/state в список накрываемых каталогов не входит — конфликта нет. (`module/default.nix`, profilesDir)

- **Профиль монтируется при запуске программы, а не при подъёме зоны.** Первым заходом слой данных накладывался прямо в zoneInit, на всю зону — и профиль оказывался намертво привязан к VPN: заблокировали сервер — настроенное окружение «уехало» вместе с ним. Теперь профиль — отдельная сущность вне каталога зон: тот же профиль можно поднять в другой зоне или вовсе без VPN. (`module/default.nix`, zoneInit + `module/vpn-profile-run.py`)

- **Слой накрывает только XDG-каталоги; документы общие намеренно.** Overlay (с опцией userxattr) — на .config, .local/share, .cache, .mozilla, .pki. Downloads/Documents и прочее содержимое $HOME общие: это разделение профилей, а не песочница. Профиль «основной» — пустая строка: слои не накладываются вовсе. (`module/vpn-profile-run.py`)

- **Одноразовый контейнер: fork+wait вместо exec, удаление только за последним жильцом.** exec нельзя — кто-то должен пережить программу и убрать каталог. Точки монтирования чистить не надо: mount namespace умирает с последним процессом. Слой стирается только когда по общему реестру запусков не осталось живых (в контейнер можно подсадить несколько программ через `--tmp-profile --join`; удаление по выходу первой отняло бы ФС у остальных). Оговорка: программа, отправляющая себя в фон с завершением первого процесса, лишится каталога из-под ног (браузеры и Electron так не делают). Брошенные при жёстком убийстве каталоги /tmp/vpn-profile-* подчищает gc. Каталоги живут в /tmp сознательно: в этой системе /tmp — btrfs на диске, а не tmpfs, кэш браузера не съест оперативку. (`module/vpn-profile-run.py`, `module/default.nix` vpn-zone run/gc)

- **«Думал, что под VPN»: у браузеров один процесс на профиль.** Второй запуск находит сокет первого, отдаёт ему «открой окно» и выходит: окно ОТКРЫВАЕТСЯ и выглядит совершенно нормально, но рисует его старый процесс в старой сети. Отличить такое поведение заранее нельзя — это свойство программы (alacritty, например, ведёт себя иначе), списком не покрыть — поэтому ПРЕДУПРЕЖДЕНИЕ с галочкой «не спрашивать снова» (kdialog --dontagain), а не запрет; проверка конфликтов — в пределах одного профиля (основной — ключ `__main__`). Из терминала без графики диалог показать негде: предупреждаем в stderr и продолжаем — молча отменять запуск хуже. По той же причине `isolate off` явно предупреждает, что браузер откроет окно в уже запущенном процессе мимо VPN. (`module/default.nix`, vpn-zone run + isolate)

- **Реестр запусков: $$ переживает exec, третье поле — селектор.** PID не меняется при exec, поэтому запись «pid зона селектор» остаётся верной всё время работы; мёртвые записи чистятся лениво при следующем запуске. Третье поле фиксирует, ЧТО было выбрано (песочница/разовая песочница/профиль): без него повторный клик по ярлыку уже запущенной программы возвращал её «голой» — сеть из реестра бралась, а песочница терялась, потому что при песочнице profile пуст и ключ каталога всегда получался `__main__`. (`module/default.nix`, vpn-zone run)

## 6. bwrap-песочница и порталы

- **`/.flatpak-info` — переключатель на порталы.** Приложение идёт через порталы, только если считает себя изолированным, а проверяет это по наличию /.flatpak-info (так делают GTK, Qt, Chromium, Electron). Хватает минимальной секции [Application]; файл монтируется только на чтение. С ним файловый диалог рисует чужой процесс и отдаёт ровно один выбранный файл (document-portal), камера и запись экрана начинают спрашивать разрешение — «андроидные» запросы получаются даром. (`module/default.nix`, vpn-fs-sandbox)

- **Разрешения: раз на программу; у именованной песочницы — на песочницу; без графики — «ничего».** Разрешения именованной песочницы общие для всех её программ — иначе вторая спрашивала бы заново про тот же самый дом. Без WAYLAND_DISPLAY/DISPLAY диалог показать негде и ждать ответа некому — программа просто зависла бы (проверено); в этом случае молча пишется пустой набор разрешений. (`module/default.nix`, vpn-fs-sandbox)

- **Идентификатор разрешений — id ярлыка, не имя бинаря.** Иначе разрешения двоятся: у Discord ярлык даёт «discord», а бинарь называется «Discord» — получались два независимых набора доступов на одну программу. Берётся VPN_ZONE_APPID (ключ пикера), имя бинаря — только при его отсутствии. (`module/default.nix`, vpn-zone run)

- **mimeapps.list пробрасывать на чтение.** В песочнице ~/.config пуст, mimeapps.list не виден, и xdg-open подбирает обработчик сам: у Discord ссылка на вход открывалась в Chrome, хотя браузер по умолчанию — zen. Файл крошечный и без секретов — пробрасывается только он и только read-only. (`module/default.nix`, vpn-fs-sandbox)

- **NVIDIA: одного /dev/dri мало.** Драйверу нужны ещё узлы /dev/nvidia*: без них EGL внутри падает («failed to create dri2 screen»), а Electron намертво виснет на заставке — проверено на Discord. (`module/default.nix`, vpn-fs-sandbox)

- **seccomp: вложенные user namespace запрещать НЕЛЬЗЯ.** У flatpak в базовом наборе такой запрет есть, но там же есть zypak, переводящий песочницу Chromium на порталы. В NixOS нет ни zypak, ни setuid chrome-sandbox, поэтому Chromium и все Electron-программы строят СВОЙ вложенный userns: запретишь `clone`/`unshare` с `CLONE_NEWUSER` — и они не стартуют вовсе («No usable sandbox! Update your kernel»). Наружу такой userns не выводит: права он даёт только над своими новыми пустыми namespace. Запрет остаётся отдельным флагом (`vpn-zone-seccomp export --deny-userns`) для программ, которые сами себя не изолируют. (`rust/src/seccomp.rs`, `module/default.nix` vpn-fs-sandbox)

- **Фильтр передаётся дескриптором, а редирект нельзя положить в массив.** `bwrap --seccomp` принимает только номер fd (не путь), поэтому файл открывается заранее (`exec 34< …`), а в массив аргументов уходит лишь `--seccomp 34`. Не собрался фильтр — предупреждение в stderr и запуск без него: мягкая деградация, как в остальных слоях. (`module/default.nix`, vpn-fs-sandbox)

- **bwrap запускать НЕ через exec; вывод dbus-прокси — в /dev/null.** После exec обработчик выхода (trap) уже не сработает, и xdg-dbus-proxy остался бы висеть. А открытый stdout прокси делает вызов «зависшим», хотя программа давно закончила. (`module/default.nix`, vpn-fs-sandbox)

- **XDG_RUNTIME_DIR — tmpfs, сокеты поимённо.** Пробрасываются только wayland-сокет (уже ограниченный wl-sandbox, если был), pipewire/pulse и прокси шины; всё остальное из runtime-каталога программе не видно. DBUS_SYSTEM_BUS_ADDRESS снимается, FLATPAK_ID выставляется. (`module/default.nix`, vpn-fs-sandbox)

- **Песочница ФС — только по явному флагу.** Включать её всем подряд нельзя: программа теряет доступ к привычным каталогам, и что именно ей нужно, выясняется поштучно. (`module/default.nix`, vpn-zone run)

## 7. Wayland и security-context

- **Механизм — помеченный сокет, а не «отказ».** Протоколы слежки (wlr-screencopy, data-control, virtual-keyboard/pointer, foreign-toplevel) выдаются любому клиенту без вопросов — в Wayland нет понятия «доверенный клиент». wp_security_context_v1: клиент создаёт ОТДЕЛЬНЫЙ unix-сокет, помечает его песочницей и отдаёт композитору; все подключившиеся через него считаются ограниченными. niri (функция client_is_unrestricted в его исходниках) и KWin такие протоколы им не выдают вовсе — программа не получает отказ, она их просто не видит (проверено: 47 протоколов против 33). Остаются: свои окна, ввод в них, буфер по Ctrl+C/Ctrl+V при фокусе, GPU, звук. (`module/wl-sandbox.c`, `module/default.nix` vpn-zone run)

- **Нет протокола — запуск без ограничений, но с предупреждением.** Старый композитор или X11-сессия: молча ослаблять защиту нехорошо, поэтому предупреждение в stderr и обычный запуск (общий путь run_plain для всех случаев «не получилось»). (`module/wl-sandbox.c`)

- **Механика сокета: close_fd-«выключатель», имя по pid, WAYLAND_SOCKET снять.** Композитор принимает соединения на помеченный сокет, пока открыт переданный ему конец трубы — держать его всё время работы программы и отпустить после выхода. Имя сокета уникально по pid: два запуска одной программы не должны драться за один путь. И обязательно `unsetenv("WAYLAND_SOCKET")`: унаследованный дескриптор перебил бы WAYLAND_DISPLAY, и программа ушла бы на обычный сокет мимо всей затеи. (`module/wl-sandbox.c`)

- **flatpak/bwrap/podman/distrobox в исключениях НЕ по недосмотру.** Они создают security-context сами, а у ограниченного клиента этот протокол как раз отобран — вложить одну песочницу в другую не выйдет. Их собственная изоляция строже нашей, пусть работают своим механизмом. (`module/default.nix`, vpn-zone run)

- **Извлечение app-id из команды полно ловушек.** Шаблон `*=*` для пропуска присваиваний переменных отбрасывал и обычные аргументы со знаком «=» внутри (строка скрипта после `sh -c`) — app-id получался пустым; пропускать надо только настоящие присваивания (`[A-Za-z_]*=*`). Id обязан быть ОДНИМ словом: пробелы разваливали аргумент wl-sandbox на два, и запускалась не та программа (проверено на `sh -c 'echo …'`). `tr -d '\n'` перед обрезкой обязателен: у многострочной команды первая строка пустая, cut отдавал пустоту, и запуск падал с «нужен app-id». (`module/default.nix`, vpn-zone run)

## 8. X11 и xwayland-satellite

- **X-сокет хоста не пробрасывается никогда.** В общем X-сервере все клиенты видят окна и ввод друг друга — дыра ровно того размера, который закрывался. Так же считает flatpak: его `--socket=x11` документирован как небезопасный, рекомендуется fallback-x11. (`module/default.nix`, vpn-fs-sandbox)

- **Свой xwayland-satellite поверх ограниченного wayland-сокета.** При разрешении x11 внутри песочницы поднимается отдельный X-сервер, где кроме приложения никого; он подключается к уже ограниченному сокету — обойти security-context через X не выйдет. После старта нужна секунда ожидания: без неё программа стартует раньше появления сокета и падает с «cannot open display». (`module/default.nix`, vpn-fs-sandbox)

- **Без разрешения x11 — DISPLAY снять, Electron уводить подсказкой.** Иначе тулкиты видят унаследованный :0, идут на X и падают вместо перехода на Wayland. Electron X не нужен: ему хватает ELECTRON_OZONE_PLATFORM_HINT=auto — проверено на Discord, который без неё падал с «Missing X server or $DISPLAY». (`module/default.nix`, vpn-fs-sandbox)

## 9. D-Bus

- **Сырая сессионная шина = доступ к паролям.** Без фильтра программа через шину дотягивается до Secret Service (то есть до KWallet со всеми паролями), до списка окон и до чужих приложений. xdg-dbus-proxy с --filter пропускает только org.freedesktop.portal.*, org.freedesktop.Notifications и org.kde.StatusNotifierWatcher. (`module/default.nix`, vpn-fs-sandbox)

- **DBusActivatable=false в перехваченных ярлыках.** Без этого лаунчер активирует программу через dbus мимо Exec — и весь перехват бесполезен. (`module/vpn-zone-sync.py`, render_picker)

## 10. .desktop и лаунчеры

- **Генерация .desktop на python, а не sed.** .desktop — ini с локализованными ключами и экранированием; разбирать его построчно значит однажды получить ярлык с поехавшим Exec. (`module/default.nix`, часть 4)

- **В Exec — никаких кавычек и пробелов.** Telegram (и не он один) разбирает Exec наивно, по пробелам, кавычки не снимая: «Zen Browser» разваливался на `Zen` и `Browser"`, и запуск падал с «невозможно выполнить Browser"». В командной строке остаются только слова без пробелов; человекочитаемое имя пикер и диалоги берут из файла меток `.labels` (в списках сброса показывается «Zen Browser», а не ключ вроде com.ayugram.desktop, по которому не догадаешься, о чём речь). (`module/vpn-zone-sync.py` render_picker, `module/default.nix` vpn-zone-pick + vpn-zone-forget-gui)

- **`--id`: стабильный ключ ярлыка вместо вычисления из команды.** Раньше ключ памяти вычислялся из первого слова команды, и для `Exec=env DESKTOPINTEGRATION=1 AyuGram` получался «env» — все такие программы делили одну память, а в списке сбросов виднелось загадочное «env». Ключ — имя .desktop без расширения; запасной разбор (для запусков мимо ярлыка) пропускает обёртки и присваивания. (`module/vpn-zone-sync.py` render_picker, `module/default.nix` vpn-zone-pick)

- **Ярлыки и пикер обновляются НЕ атомарно — разбирать оба формата аргументов.** При пересборке sync успел отработать раньше подмены профиля, и новый пикер получил ярлыки старого формата (имя программы первым аргументом) — AyuGram перестал запускаться вовсе («невозможно выполнить AyuGram Desktop»). Разбирать оба формата дешевле, чем полагаться на порядок обновления; метка принимается только если дальше в аргументах есть «--», иначе съелась бы команда. (`module/default.nix`, vpn-zone-pick)

- **Защита от самопоедания генератора.** Файлы с ключом X-VPNZone на вход не берутся; per-zone-клоны отсеиваются ещё и по префиксу имени; чужие файлы в ~/.local/share/applications (симлинки home-manager, ручные ярлыки) не перезаписываются НИКОГДА — только свои, помеченные маркером, иначе первый же sync затёр бы ярлыки, которые кладёт Nix. Собственные служебные ярлыки называются vpn-zone-* — генератор их не трогает и сам себя не перехватывает. (`module/vpn-zone-sync.py`, `module/default.nix` xdg.desktopEntries)

- **Битые симлинки: `exists()` лжёт.** Path.exists() на симлинк, указывающий в никуда, возвращает False — без отдельной проверки sync записал бы файл ПО симлинку, то есть в чужую цель (у home-manager это read-only /nix/store), и весь проход падал с OSError. Проверено: именно так и произошло. Правильная проверка занятости пути: `exists() or is_symlink()`. (`module/vpn-zone-sync.py`, occupied)

- **Писать файлы только при изменении содержимого.** За каталогом ярлыков следит path-юнит: без сравнения он будил бы sync, тот переписывал бы файлы, и цикл не заканчивался бы никогда. (`module/vpn-zone-sync.py`, write_if_changed)

- **MimeType: per-zone-клонам не давать, picker-ярлыку сохранять.** Иначе клоны начнут перехватывать ассоциации файлов, и «открыть картинку» однажды молча уедет в зону с VPN. В режиме picker наоборот: ярлык один и обязан сохранить ассоциации, иначе программа перестанет быть обработчиком; коды полей (%U, %f) тоже сохраняются — путь долетает до программы через пикер обычным аргументом. (`module/vpn-zone-sync.py`)

- **В Exec ярлыков — профильный путь vpn-zone, не store-путь.** Это разрывает зависимость по кругу (vpn-zone зовёт sync, sync подставляет vpn-zone; поэтому же `vpn-zone sync` исполняет vpn-zone-sync через PATH профиля) и ярлыки не протухают при каждом обновлении пакета — иначе после любой пересборки они указывали бы на старый store-путь до следующего sync. (`module/default.nix`, vpn-zone-sync-обёртка + vpn-zone sync)

## 11. kdialog и поведение GUI

- **Аргумент с ведущим «-» kdialog принимает за опцию и молча закрывается.** Раньше в именах профилей разрешалась только латиница, и санитизация превращала русское название в строку дефисов — kdialog закрывался без единого слова. Теперь запрещено ровно опасное: разделители пути, пробелы, ведущие дефис/точка; кириллица остаётся кириллицей. Старые каталоги с ведущим дефисом создать уже нельзя, но они могли остаться — меню их просто не показывают. (`module/default.nix`, vpn-zone profile create / sandbox create + vpn-zone-pick ask_profile)

- **Клик по ярлыку работающей программы — «разверни окно», а не вопрос.** Спрашивать сеть бессмысленно: программа с одним процессом всё равно отдаст команду запущенному экземпляру, и он останется в своей сети. Пикер находит по реестру, где она работает, и запускает туда же с тем же селектором (профиль/песочница) — окно разворачивается без диалога. (`module/default.nix`, vpn-zone-pick)

- **Сеть и контейнер закрепляются порознь.** Сначала закрепление хранило пару «сеть+контейнер», и «Всегда» в первом окне намертво фиксировало заодно и второе — неверно: это независимые оси. Теперь два файла (.pinned и .pinnedprofile), диалог показывается только для незакреплённой оси. В .pinnedprofile значение «всегда основной» — сентинел `__main__`: пустую строку не отличить от «не закреплено». (`module/default.nix`, vpn-zone-pick)

- **Закреплённая сеть + незакреплённый контейнер — отдельное окно контейнера.** Пункт «Сменить контейнер» живёт в окне выбора сети; когда сеть закреплена и окно не показывается, попасть в выбор контейнера было неоткуда — поэтому он спрашивается своим окном. Так возможно «сеть всегда одна, контейнер каждый раз выбираю». (`module/default.nix`, vpn-zone-pick)

- **Запоминать ВЫБОР, а не переменную profile.** У песочницы profile пуст (она живёт отдельным флагом fssand/sandbox), и запись «как есть» превращала её в «основной» — выбор выглядел не сохранившимся. В .lastprofile пишется селектор (`__fs__`, `sb:имя`, имя профиля); одноразовые контейнеры (`__tmp__`, `tmpjoin:`) не запоминаются — помнить их незачем. (`module/default.nix`, vpn-zone-pick)

- **Мёртвые закрепления снимать.** `vpn-zone rm` снимает закрепления, указывающие на удаляемую зону — иначе программа осталась бы привязана к несуществующей сети и молча падала бы при каждом запуске. Пикер дополнительно проверяет, что закреплённая зона/профиль ещё существуют, и сбрасывает битые записи. (`module/default.nix`, vpn-zone rm + vpn-zone-pick)

- **Вопрос о контейнере задаётся всегда, даже когда профилей ещё нет.** Сначала диалог показывался только при наличии профилей — и о функции невозможно было узнать, не читая справку: система молча решала, что контейнер не нужен. Пункт «Основной» есть всегда, рядом — «Новый профиль…»/«Новая песочница…», чтобы завести контейнер прямо из диалога. (`module/default.nix`, vpn-zone-pick ask_profile)

## 12. Bash внутри Nix: экранирование

- **`''${var:+…}` с кавычками внутри не работает.** Кавычки в такой подстановке остаются литеральными символами, аргументы разъезжаются — bwrap пытался ВЫПОЛНИТЬ номер дисплея («execvp :149»). Единственный надёжный способ собирать опциональные аргументы — bash-массивы. (`module/default.nix`, vpn-fs-sandbox)

- **printf вместо heredoc в середине Nix-строки.** Строка в реестр добавляется printf'ом: многострочная переменная с закрывающей кавычкой в нулевой колонке сбила бы снятие общего отступа в Nix indented string и разломала бы heredoc справки выше по файлу. (`module/default.nix`, vpn-zone run)

- **Абсолютные пути ко всем инструментам.** Часть кода исполняется внутри namespace, где PATH может быть каким угодно — все вызовы через ${pkgs.…}/bin/…. (`module/default.nix`, let-блок)

- **`#include "…"` не работает из /nix/store.** Заголовки ищутся относительно исходника, а тот лежит в read-only store, где ничего сгенерировать нельзя — исходник wl-sandbox.c копируется в каталог сборки рядом со сгенерированными wayland-scanner заголовками. (`module/default.nix`, деривация wl-sandbox)

## 13. systemd

- **Делегирование запуска через systemd-run --user.** systemd --user живёт в корневом namespace, его сокет виден изнутри зоны, и запущенная им команда стартует снаружи — оттуда переход в любую зону разрешён. Графическое окружение у него своё, полное (WAYLAND_DISPLAY, DBUS, XDG_RUNTIME_DIR) — проверено. Тем же способом «Прямой интернет», выбранный изнутри зоны, становится действительно прямым, а не наследует её сеть. Метки: VPN_ZONE_CURRENT помечает потомков зоны, VPN_ZONE_DELEGATED предотвращает повторное делегирование. (`module/default.nix`, vpn-zone run + vpn-zone-pick launch)

- **Пересборка ярлыков сразу после активации home-manager.** Без `home.activation` после linkGeneration порядок случайный: таймер или path-юнит могли отработать ДО подмены профиля — ярлыки оставались в старом формате при новом пикере, и запуск программ ломался до следующего срабатывания таймера. Триггеры пересборки: активация, вход в сессию, каждые 30 минут, изменение каталогов с .desktop (после nixos-rebuild там появляются новые программы). (`module/default.nix`, home.activation.vpnZoneSync + timer/path-юниты)

- **Ярлык при опущенной зоне — поднять её самому.** Это ожидаемое поведение, а не ошибка: `run` сам стартует vpn-zone@<имя>.service и ждёт файла ready. Зона переживает выход из графической сессии — живёт, пока её не погасят. (`module/default.nix`, vpn-zone run + юнит vpn-zone@)
